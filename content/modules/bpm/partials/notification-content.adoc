[[notification-expressions]]
=== Expressions in Notifications

The subject and the body are Flowable https://www.flowable.com/open-source/docs/bpmn/ch04-API/#expressions[expressions^], for example, `+${order.number}+` or `+${context.recipientUser.username}+`. Values are inserted with `toString()`, so call methods to format them, for example, `+${order.date.getYear()}+`.

The `context` object has the following properties:

[cols="1,4", options=header]
|===
|Property
|Description

|`recipientUser`
|The user who receives this notification.

|`processId`
|The id of the process instance.

|`processDefinitionId`, `processDefinitionName`
|The id and the name of the process definition.

|`executionId`
|The id of the execution.

|`variables`
|A map of the process variables, for example, `+${context.variables.orderNumber}+`.
|===

NOTE: In the subject and body, `context` always refers to the notification context, even if the process has a variable with this name.

[[notification-templates]]
=== Message Templates in Notifications

If a notification uses a message template, the template renders only the body. The subject is still taken from the *Subject* property and uses Flowable expressions, while the template uses the xref:message-templates:index.adoc#message-template-engine[FreeMarker] syntax.

The template xref:message-templates:message-templates.adoc#parameters[parameters] are filled from process variables: the alias of each parameter must match the name of a process variable. For example, if the process has the `order` variable, add the `order` parameter and use `+${order.number}+` in the template. The `context` object described in <<notification-expressions>> is available too. The default values of the parameters are not used. If the template refers to a missing variable, the notification is not sent, and the error is written to the log.

[[notification-errors]]
=== Errors in Notifications

Notifications don't interrupt the process. If an expression fails or a notification can't be sent, the error is written to the log, and the process continues. Other notifications and other recipients of the same notification are not affected.

In-app notifications are saved in a separate transaction, so they remain even if the process transaction is rolled back later. Emails are sent asynchronously by the xref:email:index.adoc[Email Sending] add-on. A recipient without an email address gets no email, and a warning is written to the log.

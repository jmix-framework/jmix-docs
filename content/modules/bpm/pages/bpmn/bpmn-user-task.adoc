= Пользовательская задача

[[overview]]
== Обзор
*Пользовательская задача* — это задача, которая назначается пользователю или группе для выполнения вручную в рамках бизнес-процесса.
Пользовательские задачи — неотъемлемая часть рабочего процесса: через них люди взаимодействуют с процессом,
выполняя конкретные действия, принимая решения или вводя данные.

[NOTE]
====
*Один исполнитель или группа*

В BPMN у задачи может быть только один исполнитель.
Когда говорят «задача назначена группе»,
имеют в виду список *потенциальных исполнителей*, а не объект *UserGroup*.
Один из них должен стать фактическим исполнителем, xref:bpmn/bpmn-user-task.adoc#claiming-group-tasks[забрав] задачу.
====

[[graphical-notation]]
.*Графическая нотация*

Пользовательская задача изображается как обычная задача (прямоугольник со скругленными углами) с небольшим значком пользователя в левом верхнем углу.

image::bpmn-user-task/user-task.png[,120]

.*XML-представление*
В XML пользовательская задача определяется так.
Атрибут `id` обязателен, атрибут `name` необязателен.

[source,xml]
----
<userTask id="user-task-01" name="User task" />
----

[[due-date]]
== Срок выполнения

Параметр *срок выполнения* (due date) пользовательской задачи задает крайний срок, к которому задача должна быть выполнена.
Этот параметр важен для управления действиями процесса, зависящими от времени.

NOTE: Срок выполнения сам по себе не запускает никаких автоматических действий. Последующие действия нужно настроить вручную.

[[setting-due-date]]
=== Задание срока выполнения
Параметр _Due date_ можно задать двумя способами:

* *Фиксированная дата*: дата в будущем, которая означает крайний срок.
(Дата в прошлом игнорируется, задача будет показана как просроченная.)
* *Длительность*: период времени, отсчитываемый с момента создания задачи.

Фактически срок выполнения — это текстовое поле, которое движок процессов интерпретирует во время выполнения.
Доступны следующие варианты:

* Строка в формате *ISO8601*, задающая фиксированную дату или длительность.
* Переменная процесса типа:
** `java.lang.String` — должна содержать значение в формате *ISO8601*.
** `java.util.Date` — должна содержать дату.
* Выражение, которое во время выполнения вычисляется в один из вариантов выше, например `$/{someDateVariable/}`.

[NOTE]
====
* Если значение переменной равно `null`, ошибки не возникает. Это означает, что у задачи нет крайнего срока.
* Параметр _Due date_ не проверяется при развертывании процесса.
Но во время выполнения неверное значение вызовет ошибку.
====

*Примеры ISO 8601*

* Фиксированная дата:
** 2024-02-01T08:40:37
** 2050-01-01
* Длительность:
** PT20M — через 20 минут
** PT5H — через 5 часов
** PT3D — через 3 дня

[[accessing-due-date-programmatically]]
=== Работа со сроком выполнения из кода

Параметром _due date_ можно управлять с помощью методов класса `Task`:

[source,java]
----
Task task = taskService.createTaskQuery()
                .taskId("taskId").singleResult(); <1>
task.getDueDate(); <2>
task.setDueDate(null); <3>
taskService.saveTask(task); <4>
----
<1> получение задачи по id
<2> получение текущего срока выполнения
<3> установка нового срока выполнения, равного `null`
<4> сохранение объекта задачи

Так можно динамически менять сроки выполнения в зависимости от бизнес-логики.
Например, исполнитель может попросить дополнительное время на выполнение задачи.

[[using-business-calendar]]
=== Использование бизнес-календаря

Если установлено дополнение *Business Calendars*,
в разделе свойств _General_ на экране *Web BPM Modeler* появляется поле бизнес-календаря:

image::bpmn-user-task/busines-calendar.png[,400]

Здесь можно выбрать один из заранее настроенных бизнес-календарей в выпадающем списке.
В этом случае срок выполнения можно задать только как длительность, а прошедшее время рассчитывается с учетом бизнес-календаря.

Например, пользователь получил задачу в 16:00.
В бизнес-календаре стандартное рабочее время — с 10:00 до 18:00,
а срок выполнения задан как 3 часа (`PT3H`).

Крайний срок будет не в 19:00, через 3 часа, а в 11:00 следующего рабочего дня.
С бизнес-календарем учитываются только рабочие часы.

[NOTE]
====
С бизнес-календарем длительность можно задать в часах и минутах, но не в днях.
====

*XML-представление*
Пользовательская задача со сроком выполнения:

[source,xml]
----
<userTask id="Activity_0gsy9yk" name="User task"
    flowable:dueDate="PT3H" <1>
    flowable:businessCalendarName="test-calendar"> <2>
. . .
</userTask>
----
<1> срок выполнения в виде длительности
<2> атрибут бизнес-календаря

Подробнее см. в описании дополнения xref:jmix:business-calendar:index.adoc[Business Calendars].

[[user-assignment]]
== Назначение исполнителя

Чтобы задачу можно было выполнить, ей нужно назначить исполнителя.
Исполнителем задачи может быть назначен *только один* пользователь, его называют *assignee*.

Атрибут `assignee` может быть пустым. Это значит, что ни у одного пользователя эта задача не отображается в списке задач.
Обычно такая задача считается _групповой_: у нее есть список потенциальных исполнителей, или _кандидатов_.
Кроме того, исполнителя можно назначить во время выполнения — с помощью административных функций или из кода.

[[assigne-sources]]
=== Источники исполнителя

В Jmix BPM _источник исполнителя_ (assignee source) — это способ, которым определяется пользователь, назначаемый исполнителем конкретной пользовательской задачи в бизнес-процессе.
Есть три варианта:

[horizontal]
Expression:: Выражение, результат которого — строка с именем пользователя.
Process variable:: Переменная, которая ссылается на сущность _User_.
User provider:: Java-класс с методом, который возвращает имя пользователя.

image::bpmn-user-task/assignee-sources.png[,460]

[[assign-taask-by-expression]]
==== Назначение задачи по выражению

Выражение — источник исполнителя по умолчанию.
Нужно написать выражение, которое вычисляет имя пользователя-исполнителя.
Например, если сущность `User` хранится в переменной процесса `manager`, выражение будет таким: `${manager.username}`:

image::bpmn-user-task/assign-by-expression.png[,460]

*XML-представление*
[source,xml]
----
<userTask id="user-task-01" name="User task"
    flowable:assignee="${manager.username}"
    jmix:assigneeSource="expression"
    jmix:assigneeValue="${manager.username}" />
----

Чтобы назначить задачу конкретному пользователю, можно указать имя пользователя напрямую:

image::bpmn-user-task/assigne-by-expression-direct.png[,460]

Также можно вызвать метод бина Spring, который возвращает имя пользователя:

 ${smpl_MyBean.evaluateManager(methodParam1, 'methodParam2')}

[[assign-task-by-process-variable]]
==== Назначение задачи по переменной процесса

Если выбрать источник исполнителя *Process variable*, на панели свойств появляется компонент _ComboBox_. В нем отображаются поля и переменные процесса типа `Entity`, класс сущности которых реализует интерфейс `UserDetails`.

*Встроенная переменная `initiator`*

При моделировании процесса для назначения задач доступна встроенная переменная процесса `initiator`. Она содержит сущность пользователя, который запустил процесс:

image::bpmn-user-task/assignee-initiator.png[,460]

*XML-представление*

Пользовательская задача с исполнителем, назначенным по переменной процесса:

[source,xml]
----
<userTask id="user-task-01" name="User task"
    camunda:assignee="${initiator.username}"
    jmix:assigneeSource="processVariable"
    jmix:assigneeValue="initiator" />
----

[CAUTION]
====
Если процесс запущен через API или сообщением либо сигналом, переменная `initiator` не определена.
Ее использование может вызвать ошибку во время выполнения.
====

Переменную процесса `initiator` можно отключить с помощью следующего свойства:

[source,properties,indent=0]
----
jmix.bpm.process-initiator-variable-enabled=false
----

Также можно изменить имя переменной initiator:

[source,properties,indent=0]
----
include::example$/ex1/src/main/resources/application.properties[tags=name]
----

[[assign-task-by-user-provider]]
==== Назначение задачи через поставщика пользователей

Если для определения исполнителя задачи нужна сложная бизнес-логика, лучше выбрать вариант *User provider*.
В этом случае система предлагает выбрать существующий Java-класс поставщика пользователей:

image::bpmn-user-task/selecting-user-provider.png[,460]

Класс поставщика пользователей должен реализовать один или несколько методов, возвращающих `String`.
Метод получает значения параметров, заданные в моделере, и возвращает имя пользователя, который становится исполнителем задачи.

*XML-представление*

Пользовательская задача с исполнителем, назначенным через поставщика пользователей:
[source,xml]
----
<userTask id="user-task" name="User task" jmix:assigneeSource="userProvider" jmix:assigneeValue="smpl_MyUserProvider">
  <extensionElements>
    <jmix:springBean beanName="smpl_MyUserProvider" methodName="getUser" />
  </extensionElements>
</userTask>
----

Класс поставщика пользователей — это обычный бин Spring с аннотацией `@UserProvider`.
Вот пример поставщика пользователей, который читает переменную процесса с адресом электронной почты пользователя и находит пользователя в базе данных.

[source,java,indent=0]
----
include::example$/ex1/src/main/java/bpm/ex1/service/MyUserProvider.java[tags=user-provider]
----
В классе `UserProvider` можно реализовать любые бизнес-правила.
Например, выбрать наименее загруженного пользователя из роли или отдела, выбрать следующего по очереди или хотя бы случайного пользователя из группы.

[[assigning-task-by-lane]]
=== Назначение задач по полосе

Пользовательская задача, расположенная на xref:bpmn/bpmn-pools-lanes.adoc#lanes[полосе], может получать исполнителя и кандидатов от полосы. Чтобы задать их, выберите полосу:

[cols="1,6", grid=rows, frame=none]
|===
|*Свойство*
|*Описание*
include::partial$element-properties.adoc[tags=id;name]
|Assignee source
|Назначение исполнителя по выражению, переменной процесса или через поставщика пользователей. См. <<assigne-sources>>.
|Candidate groups
|Группа пользователей, которым разрешено выполнять действия в пределах полосы.
|Candidate users
|Отдельные пользователи, которым разрешено выполнять действия в пределах полосы.
include::partial$element-properties.adoc[tag=documentation]
|===

При развертывании процесса движок проверяет каждую пользовательскую задачу на полосе. Если у задачи нет ни исполнителя, ни групп-кандидатов, она получает исполнителя, пользователей-кандидатов и группы-кандидатов, заданные полосой. Пользователи-кандидаты полосы заменяют собственных пользователей-кандидатов задачи. Если у задачи есть исполнитель или группы-кандидаты, движок игнорирует полосу.

В XML полосы представлены элементом `laneSet` и его элементами `lane`. Каждый элемент `lane` содержит свойства назначения и список размещенных на полосе элементов.

[source,xml]
----
<process id="pool-and-lanes" name="Pool and lanes" isExecutable="true">
    <laneSet id="LaneSet_1lxq2l3">
      <lane id="Lane_1" name="User 1">
        <extensionElements>
          <jmix:assignmentDetails assigneeSource="expression" assigneeValue="user1" assignee="user1" candidateUsersSource="users" candidateGroupsSource="userGroups" />
        </extensionElements>
        <flowNodeRef>Activity_0n34ol9</flowNodeRef>
        <flowNodeRef>Activity_0758bjc</flowNodeRef>
        <flowNodeRef>Event_1mkoyrv</flowNodeRef>
      </lane>
      <lane id="Lane_2" name="User 2">
        ...
      </lane>
    </laneSet>
----

[[assigning-task-programmaticaly]]
=== Назначение задачи из кода

Чтобы задать _исполнителя_ задачи из кода, используйте метод `setAssignee` сервиса `TaskService`. Пример:

[source,java]
----
Task task = taskService.createTaskQuery()
                       .taskId("taskId")
                       .singleResult(); <1>

taskService.setAssignee(task.getId(), "jane"); <2>
----
<1> получение объекта задачи через Query API
<2> назначение исполнителя по имени пользователя

Задачи, назначенные определенному пользователю, можно получить через `TaskService` так:

[source,java]
----
List<Task> tasks = taskService.createTaskQuery()
    .taskAssignee("jane") <1>
    .list();
----
<1> имя пользователя

[[task-candidate-users-and-groups]]
== Пользователи-кандидаты и группы-кандидаты задачи

*Кандидаты* — это пользователи или группы, которые могут забрать задачу и выполнить ее.
Если у задачи несколько кандидатов, задача появляется в списках задач всех кандидатов.
Первый кандидат, который забирает задачу, становится _исполнителем_ и может выполнить задачу.
После этого задача перестает быть видна другим кандидатам.

[NOTE]
====
Под «группами» здесь технически понимается список кодов *User group*.
====

[[claiming-group-tasks]]
=== Как забрать групповую задачу

Часто не важно, какой именно пользователь выполнит задачу.
Например, менеджеру все равно, кто из двух бухгалтеров примет решение по его заказу.

В этом случае Jmix BPM позволяет назначить задачу _списку кандидатов_, и исполнителем может стать любой из них.
Но сначала он должен _забрать_ задачу.
Забрать задачу — значит назначить ее на себя.

Задача с кандидатами появляется на экране xref:bpm:bpmn/multi-instance-activities.adoc[*My tasks*] в разделе *Group tasks* у каждого кандидата.

image::bpmn-user-task/my-tasks-claim.png[,300]

После того как один из кандидатов забирает задачу, она переходит в список *Assigned tasks* этого пользователя и исчезает из списка *Group tasks* остальных кандидатов.

image::bpmn-user-task/claiming-form.png[,450]

Чтобы забрать задачу, пользователь должен открыть ее и выполнить одно из действий:

* *Claim and resume* — пользователь становится исполнителем задачи, форма задачи открывается заново в обычном режиме, и с ней можно продолжить работу.
* *Claim and close* — пользователь становится исполнителем задачи, форма задачи закрывается; позже ее можно найти в разделе _Assigned tasks_ списка задач:

image::bpmn-user-task/my-tasks-claimed-task.png[,300]

[[claiming-task-programmatically]]
=== Как забрать задачу из кода

Через API задачу можно забрать от имени указанного пользователя:

[source,java]
----
taskService.claim("taskId", "userId");
----

[[user-groups-provider]]
==== Поставщик групп пользователей

Если при задании групп-кандидатов нужна сложная логика, лучше выбрать вариант _User groups provider_.

image::bpmn-user-task/selecting-user-group-provider.png[,450]

Он позволяет выбрать один из ранее созданных бинов Java с аннотацией `@UserGroupListProvider`.
Этот бин должен реализовать один или несколько методов, которые возвращают `List<String>` с кодами групп пользователей.

У аннотации `@UserGroupListProvider` два атрибута:

* *value* — имя, которое отображается в моделере.
* *description* — необязательное пояснение назначения метода.

Пример:

[source,java]
----
@UserGroupListProvider(value="allGroups",
                       description = "Returns a list of all groups")
public class MyGroupListProvider {

    @Autowired
    private UserGroupService userGroupService;

    public List<String> getAllUserGroups() {
        List<UserGroup> allUserGroups = userGroupService.getAllUserGroups();
        if (!allUserGroups.isEmpty()) {
            return allUserGroups.stream().map(UserGroup::getCode).toList();
        } else {
            return Collections.emptyList();
        }
    }
}
----

Подробнее см. в разделе xref:bpm:menu-views/user-groups.adoc[User groups].

* *User groups* — выбор имен пользователей из списка.
* *User groups provider* — выбор специального Java-класса, который возвращает список имен пользователей.
* *Expression* — получение списка имен пользователей из выражения.

[[user-list-provider]]
==== Поставщик списка пользователей

Как и в случае с _User Groups Provider_, список пользователей-кандидатов можно получить из кода,
вызвав метод бина Spring с аннотацией `@UserListProvider`:

image::bpmn-user-task/candidate-user-list-provider.png[,450]

Пример:

[source,java]
----
@UserListProvider(value = "smpl_UserListProviderDemo",
                  description = "Get all users")
public class UserListProviderDemo {

    @Autowired
    private DataManager dataManager;
    @Autowired
    private SystemAuthenticator authenticator;

    public List<String> getAllUsers() {
        authenticator.begin();
        try {
            List<User> users = dataManager.load(User.class).all().list();
            return users.stream().map(User::getUsername).toList();
        } finally {
            authenticator.end();
        }
    }
}
----

[[setting-task-listeners]]
== Настройка слушателей задач

Пользовательские задачи в Jmix BPM поддерживают слушатели задач, которые выполняют собственную логику в ответ на события задачи.
Слушатели задач позволяют задать Java-классы или выражения,
которые срабатывают при событиях пользовательской задачи.

image::bpmn-user-task/task-listeners-field.png[,460]

Слушатели задач могут реагировать на следующие события пользовательской задачи:

- *create*: срабатывает, когда пользовательская задача создана и заданы ее свойства, включая исполнителя.
- *assignment*: срабатывает, когда меняется исполнитель пользовательской задачи. Если задача получает исполнителя при создании, *assignment* срабатывает перед *create*. Добавление пользователей-кандидатов или групп-кандидатов его не вызывает.
- *complete*: срабатывает, когда пользовательская задача выполнена, перед *delete*.
- *delete*: срабатывает перед удалением пользовательской задачи из данных времени выполнения — после *complete* или когда задача удаляется, например вместе с экземпляром процесса.

Чтобы настроить слушатель задач для пользовательской задачи, используйте элемент расширения `flowable:taskListener` в BPMN XML
или метод `addTaskListener` в Java API.

Слушатели задач — мощный механизм, который расширяет поведение пользовательских задач
и встраивает в процессы собственную логику.
С их помощью можно отправлять уведомления, обновлять внешние системы
или выполнять дополнительные проверки в ответ на события жизненного цикла пользовательской задачи.

*XML-представление*
[source,xml]
----
<userTask id="approve-invoice" name="Approve invoice" jmix:assigneeSource="expression">
  <extensionElements>
    . . .
    <flowable:taskListener class="com.company.demo.listener.ApproverAssignment" <1>
                           event="assignment" /> <2>
  </extensionElements>
 . . .
</userTask>
----
<1> Класс слушателя задач
<2> Событие задачи

[[notifications]]
== Уведомления

[.since]
Начиная с Jmix 3.1

Пользовательская задача может отправлять уведомления в приложении и по электронной почте через дополнение xref:notifications:index.adoc[Notifications], поэтому это дополнение обязательно. Без него моделер не показывает раздел *Notifications* пользовательских задач, а во время выполнения процесс не отправляет уведомления.

Другие дополнения расширяют эти возможности:

* xref:email:index.adoc[Email Sending] включает канал *Email*. См. xref:notifications:configuration.adoc#email-channel[Канал Email].
* xref:message-templates:index.adoc[Message Templates] позволяет формировать текст из шаблона. См. <<notification-templates>>.

Чтобы выбирать тип уведомления в моделере, зарегистрируйте типы, как описано в разделе xref:notifications:configuration.adoc#notification-types[Типы уведомлений]. Чтобы читать уведомления в приложении, получателям нужна роль, описанная в разделе xref:notifications:configuration.adoc#roles[Роли безопасности].

Каждое уведомление отправляется при событии задачи, выбранном в его свойстве *Event*: *create*, *assignment*, *complete* или *delete*. Это события <<setting-task-listeners,слушателей задач>>, и Jmix BPM добавляет эти слушатели при развертывании процесса. Движок генерирует *delete*, когда задача выполнена, сразу после *complete*, а также когда прерывающее граничное событие отменяет задачу или удаляется экземпляр процесса.

Чтобы отправить уведомление в другой момент, прикрепите к задаче граничное событие и соедините его с xref:bpmn/jmix-notification-task.adoc[задачей отправки уведомления]. Например, непрерывающее граничное событие xref:bpmn/bpmn-events.adoc#timer-events[таймера] может уведомить инициатора процесса, что задача не выполнена вовремя.

*XML-представление*

[source,xml]
----
<userTask id="approve-order" name="Approve order">
  <extensionElements>
    <jmix:notification event="assignment" recipientType="assignee"
                       channels="in-app" contentType="plain">
      <jmix:subject>Task assigned: ${context.taskName}</jmix:subject>
      <jmix:body>Hello ${context.recipientUser.username}, please approve order ${order.number}.</jmix:body>
    </jmix:notification>
  </extensionElements>
</userTask>
----

В уведомлениях пользовательской задачи у объекта `context`, описанного в разделе <<notification-expressions>>, также есть свойства `taskId` и `taskName` с id и именем задачи и свойство `taskAssigneeUser` с ее исполнителем.

[[notification-properties]]
=== Свойства уведомления

Раздел *Notifications* показывает список уведомлений. Для управления ими используйте кнопки *Create*, *Edit* и *Remove*. У уведомления есть следующие свойства:

[cols="1,6", grid=rows, frame=none]
|===
|*Свойство*
|*Описание*

|Subject
|Тема уведомления. Обязательное свойство. Может содержать <<notification-expressions,выражения>>.

|Type
|Необязательный тип уведомления. Задает значок уведомления в UI. Список показывает xref:notifications:configuration.adoc#notification-types[зарегистрированные типы]; также можно ввести имя типа.

|Event
|Событие задачи, при котором отправляется уведомление. Обязательное свойство. См. <<notifications>>.

|Recipient
|Кто получает уведомление. Обязательное свойство. См. <<notification-recipients>>.

|Recipient expression
|Выражение, которое возвращает получателей. Показывается, если *Recipient* имеет значение *Expression*.

|Channels
|*In-app*, *Email* или оба. Нужен хотя бы один канал. По умолчанию выбран *In-app*. *Email* доступен, если установлено дополнение xref:email:index.adoc[Email Sending].

|Use message template, Message template
|Шаблон, по которому формируется текст. Доступно, если установлено дополнение xref:message-templates:index.adoc[Message Templates]. См. <<notification-templates>>.

|Content type
|*Plain text* или *HTML*. Для HTML текст редактируется в редакторе форматированного текста. Если переключиться с HTML на обычный текст, моделер запрашивает подтверждение и очищает текст. Скрыто, если используется шаблон сообщения.

|Body
|Текст уведомления. Может содержать <<notification-expressions,выражения>>. Скрыто, если используется шаблон сообщения.
|===

В XML каждое уведомление — это элемент расширения `jmix:notification`. Его атрибуты: `recipientType`, `recipientExpression`, `channels`, `type`, `contentType` и `templateCode`; дочерние элементы: `jmix:subject` и `jmix:body`. Атрибут `event` хранит событие.

[[notification-recipients]]
=== Получатели уведомлений

[cols="1,1,4", options=header]
|===
|Recipient
|Значение в XML
|Описание

|Task assignee
|`assignee`
|Если у задачи нет исполнителя, уведомление не отправляется.

|Candidate users
|`candidateUsers`
|См. <<task-candidate-users-and-groups>>.

|Candidate groups
|`candidateGroups`
|Все пользователи групп-кандидатов задачи, в соответствии с xref:menu-views/user-groups.adoc#user-group-editor[типом группы].

Каждый получатель получает отдельное уведомление, а тема и текст формируются для этого получателя. Пользователь получает одно уведомление, даже если он найден несколько раз, например в двух группах-кандидатах. Имя пользователя, которому не соответствует существующий пользователь, пропускается.

[[task-documentation]]
== Документация
Дополнительную информацию для пользователя можно указать в параметре _documentation_ (так он называется в BPMN) или _description_ (так он называется в API).
Его длина не может превышать 4000 символов.

Изначально поле _documentation_ было предназначено для документирования модели процесса аналитиками.
Но в пользовательской задаче его можно рассматривать как инструкцию для пользователя, объясняющую, что нужно сделать.

Это поле находится в самом конце панели свойств.

TIP: Поле _documentation_ можно обновлять при каждом изменении процесса.
Это самый простой и эффективный способ давать пользователям актуальную информацию.

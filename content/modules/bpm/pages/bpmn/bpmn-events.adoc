= Events

An event is something that happens while a process runs: a timer fires, a message arrives, a step fails with a business error. Events start and end paths, make the process wait, and change its path.

[[event-element-types]]
== Event Element Types

An event has a position in the process and a trigger. By position, an event is one of the following:

* A start event starts a process instance or a subprocess. In an xref:bpmn/bpmn-subprocesses.adoc#event-subprocess[event subprocess], its trigger starts the event subprocess.
* An intermediate event is on a sequence flow between two elements.
* A boundary event is attached to an activity: a task, a subprocess, or a call activity. It reacts to its trigger while the activity runs. A compensation boundary event is the exception: it becomes active when the activity completes. In the Modeler view, drag an intermediate event from the palette onto the border of an activity to attach it.
* An end event ends a path.

By trigger, an event is a none, timer, message, signal, error, escalation, compensation, cancel, or terminate event. The table below shows which triggers are available in which position.

A catching event waits for its trigger. Start events, boundary events, and intermediate catching events are catching events. A throwing event creates a trigger for catching events, for example, throws an error or a signal. Intermediate throwing events and end events are throwing events, but none events throw nothing.

An intermediate catching event is a xref:bpmn/transactions.adoc#waiting-states[wait state]: the process stops there, the engine commits the transaction and stores the process state, and the process continues when the trigger arrives. The engine waits for messages and signals through <<event-subscriptions,event subscriptions>> and for timers through timer jobs.

Boundary events and the start events of event subprocesses can be interrupting or non-interrupting. Error and cancel events are always interrupting.

* An interrupting boundary event cancels the activity, and the process continues along the outgoing sequence flow of the event.
* An interrupting start event of an event subprocess cancels everything else in its scope. When the event subprocess completes, the scope completes too.
* A non-interrupting event starts its path in parallel, and the activity or the scope keeps running.

The scope of an event is the process instance or the subprocess that contains it. When an error or an escalation is thrown, the engine looks for a catching event in the scope of the throwing event first, and then in the enclosing scopes.

== Choosing an Event

[cols="3,2", options=header]
|===
|To
|Use

|Start a process from the Start process view or from code
|<<none-events,None start event>>

|Start a process on a schedule
|<<timer-events,Timer start event>>

|Pause a process for some time or until a date
|<<timer-events,Timer intermediate catching event>>

|Remind the assignee or take further steps when a task takes too long
|<<timer-events,Timer boundary event>>: non-interrupting to keep the task, interrupting to cancel it

|Start a process when your code sends a named message
|<<message-events,Message start event>>

|Wait until your code reports something about one process instance, such as a received payment
|<<message-events,Message intermediate catching event>> or message boundary event

|Notify many process instances at once, such as about a changed price list
|<<signal-events,Signal events>>

|Leave the normal path because of a business failure, such as a declined payment
|<<error-events,Error events>>

|Report a situation to an enclosing scope, with or without stopping the work
|<<escalation-events,Escalation events>>

|Undo steps that have completed
|<<compensation-events,Compensation events>>

|Cancel a transaction subprocess and undo its completed steps
|<<cancel-events,Cancel events>>

|Stop all parallel paths when one path finishes
|<<terminate-end-event,Terminate end event>>

|Mark a milestone
|<<none-events,None intermediate throwing event>>
|===

Some events are easy to confuse:

* Message or signal. A message goes to one execution that your code selects, or starts one process. A signal goes to every event that waits for it. Use a signal only when all waiting process instances must react.
* Error or escalation. An error always interrupts, and if no event catches it, the engine throws an exception. An escalation can be caught without interrupting, and if no event catches it, the engine ignores it.
* None end event or terminate end event. A none end event ends only its own path, and parallel paths go on. A terminate end event ends all paths in its scope.
* Error or compensation. An error moves the process to another path. Compensation undoes steps that have already completed, usually on that other path.

[[event-subscriptions]]
== Event Subscriptions

An event subscription is a record that tells the process engine that a process waits for a message or a signal. Only message and signal events wait through subscriptions. Timers use timer jobs, see <<timer-events>>. Error and escalation events need neither: the engine looks for a catching event when an error or an escalation is thrown.

The engine creates subscriptions as follows:

* *Start events* – a message or signal start event of a process gets a subscription when the process definition is deployed. When the message or signal arrives, a new process instance starts.
* *Intermediate events / boundary events* – a message or signal catching event gets a subscription when the process arrives at the event or, for a boundary event, when the activity it is attached to starts. When the message or signal arrives, the engine finds the matching subscription, and the execution continues.

The engine stores subscriptions in the `ACT_RU_EVENT_SUBSCR` database table.

=== Event Subscriptions API

==== Querying Event Subscriptions

You can query for existing event subscriptions to see which processes are waiting for specific events. For example:

[source,java]
----
List<EventSubscription> messageSubscriptions = runtimeService.createEventSubscriptionQuery()
    .eventType("message")
    .list();
----

==== Getting Event Subscriptions

You can get a list of subscriptions using `RuntimeService` API.
For example, signal subscriptions:

[source,java]
----
// Query for all signal event subscriptions
List<EventSubscription> signalSubscriptions = runtimeService.createEventSubscriptionQuery()
    .eventType("signal")
    .list();
----

For message subscriptions, use `"message"`. The engine also keeps `"compensate"` subscriptions for completed activities that have a compensation handler.

For timers, use `ManagementService`:

[source,java]
----
List<Job> timerJobs = managementService.createTimerJobQuery().list();
----

==== Triggering Event Subscriptions

You can trigger event subscription when the corresponding event occurs. For example, to trigger a message event:

[source,java]
----
runtimeService.messageEventReceived("orderPlaced", executionId, processVariables);
----

==== Handling Events with Listeners

See the xref:bpm:jmix-listeners.adoc[] section.


[[none-events]]
== None Events

A none event has no trigger. Most processes start with a none start event and end with none end events. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#none-start-event[None Start Event^] and https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#intermediate-throwing-none-event[Intermediate Throwing None Event^] in the Flowable documentation.

[cols="1,3", options=header]
|===
|Event
|Usage

|[[none-start-event]]None start event
|Starts a process instance when a user starts the process in the xref:menu-views/start-process-view.adoc[Start process] view or code calls `runtimeService.startProcessInstanceByKey()` with the process id. A process can have only one none start event at the process level. With a second one, the process fails to deploy with `Multiple none start events are not supported`. The start event of an xref:bpmn/bpmn-subprocesses.adoc#embedded-subprocess[embedded subprocess] is always a none start event.

|[[intermediate-none-event]]None intermediate throwing event
|The process passes through the event without waiting. Use it to mark a state that the process has reached, such as a milestone.

|[[none-end-event]]None end event
|Ends the current path. The process instance ends when no paths are active.
|===

[[timer-events]]
== Timer Events

A timer event fires at a date, after a duration, or on a repeating cycle. Use timers to start processes on a schedule, to pause a process, and to set deadlines and reminders on tasks. The xref:job-executor.adoc[job executor] runs the timers. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#timer-event-definitions[Timer Event Definitions^] in the Flowable documentation.

To add a timer event in the xref:menu-views/modeler-web.adoc[Modeler] view, click the *Change type* image:quick-start/change-type-icon.png[width="20"] icon of a start, intermediate, or boundary event and select a timer option.

[cols="1,3", options=header]
|===
|Event
|Usage

|[[timer-start-event]]Timer start event
|Starts a process instance when the timer fires. A cycle timer starts an instance on each occurrence. The engine creates the timer when the process is deployed, and deploying a new version of the process replaces it. A process started by a timer has no xref:bpmn/bpmn-user-task.adoc#assign-task-by-process-variable[`initiator`] variable, because no user starts it.

In an xref:bpmn/bpmn-subprocesses.adoc#event-subprocess[event subprocess], starts the event subprocess and can be interrupting or non-interrupting. An embedded subprocess can't have a timer start event.

|[[timer-intermediate-event]]Timer intermediate catching event
|The process waits at the event until the timer fires. The event is a xref:bpmn/transactions.adoc#waiting-states[wait state].

|[[timer-boundary-event]]Timer boundary event
|Fires if the activity it is attached to is still active when the timer fires. Can be interrupting or non-interrupting.
|===

[[timer-values]]
=== Timer Values

[[timer-types]][[setting-time]]The *Timer type* property defines how the engine reads the timer value:

[cols="1,3,2", options=header]
|===
|Timer type
|Value
|Examples

|Duration
|An ISO 8601 duration. For a start event, the engine counts it from the deployment. For other timer events, it counts from the moment the process reaches the event or the activity that the event is attached to.
|`PT8H`: 8 hours.

`P5D`: 5 days.

|Date
|An ISO 8601 date and time. If the date has passed, the timer fires right away.
|`2035-06-17T09:00:00`

|Cycle
|An ISO 8601 repeating interval or a cron expression. The first field of a cron expression is seconds.
|`R3/PT10H`: 3 times, every 10 hours.

`0 0 9 ? * MON`: every Monday at 9:00.
|===

A value can be an expression that returns such a string, for example, `+${reviewPeriod}+`. Use cron expressions only with the *Cycle* type. With other types, the engine can't create the timer and throws an exception: `couldn't resolve duedate`.

[[timer-example]]
=== Example

In this example, the process starts every Monday at 9:00. The `Write report` user task has two timer boundary events. After an hour, the non-interrupting `1 hour` event creates the `Remind performer` task, and `Write report` stays active. After five days, the interrupting `5 days` event cancels `Write report` and creates the `Escalate issue` task. When the report is written, the `Next day` event holds the process for a day before the `Check report` task.

image::bpmn-events/timer-events-example.png[,500]

The XML of this example:

[source,xml]
----
<process id="weekly-report" isExecutable="true">
  <startEvent id="every-week" name="Every week">
    <timerEventDefinition>
      <timeCycle>0 0 9 ? * MON</timeCycle> <1>
    </timerEventDefinition>
  </startEvent>
  . . .
  <userTask id="write-report" name="Write report" />
  <boundaryEvent id="one-hour" name="1 hour" attachedToRef="write-report"
      cancelActivity="false"> <2>
    <timerEventDefinition>
      <timeDuration>PT1H</timeDuration>
    </timerEventDefinition>
  </boundaryEvent>
  <boundaryEvent id="five-days" name="5 days" attachedToRef="write-report"> <3>
    <timerEventDefinition>
      <timeDuration>P5D</timeDuration>
    </timerEventDefinition>
  </boundaryEvent>
  . . .
  <intermediateCatchEvent id="next-day" name="Next day">
    <timerEventDefinition>
      <timeDuration>P1D</timeDuration>
    </timerEventDefinition>
  </intermediateCatchEvent>
  . . .
</process>
----
<1> A cron expression: every Monday at 9:00.
<2> A non-interrupting boundary event.
<3> An interrupting boundary event. Omitting `cancelActivity` is the same as setting it to `true`.

[[message-events]]
== Message Events

A message event waits for a message that your code sends to a process instance, or starts a process instance when the message arrives. Use it when another system or your application must tell one specific process instance that something has happened, for example, that a payment has arrived. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#message-event-definitions[Message Event Definitions^] in the Flowable documentation.

To add a message event in the xref:menu-views/modeler-web.adoc[Modeler] view, click the *Change type* image:quick-start/change-type-icon.png[width="20"] icon of a start, intermediate, or boundary event and select a message option.

[cols="1,3", options=header]
|===
|Event
|Usage

|[[message-start-event]]Message start event
|Starts a process instance when your code sends the message. In an xref:bpmn/bpmn-subprocesses.adoc#event-subprocess[event subprocess], starts the event subprocess when the process instance receives the message, and can be interrupting or non-interrupting. An embedded subprocess can't have a message start event.

|[[message-intermediate-catching-event]]Message intermediate catching event
|The process waits at the event until it receives the message. The event is a xref:bpmn/transactions.adoc#waiting-states[wait state].

|[[boundary-message-events]]Message boundary event
|Catches the message while the activity it is attached to is active. Can be interrupting or non-interrupting.
|===

[[sending-messages]]
=== Sending Messages

Message events refer to message definitions of the process. A definition has an id and a name. You can manage definitions in the xref:bpmn/bpmn-process.adoc#properties[process properties] or add one from an event by selecting *Create new...* in its *Message* field.

Your code sends messages through `RuntimeService` and passes the message name, not the id:

* `startProcessInstanceByMessage(messageName)` starts a process instance at a message start event. If no deployed process has a start event for the message, the call fails with `no subscription to message with name ... found`. A message can start only one process: deploying another process with a start event for the same message fails with `there already is a message event subscription for the message with name ...`.
* `messageEventReceived(messageName, executionId)` delivers the message to an execution that waits for it. If the execution doesn't wait for the message, the call fails with `does not have a subscription to a message event with name ...`. Find the execution by the message name:
+
[source,java]
----
Execution execution = runtimeService.createExecutionQuery()
        .processInstanceId(processInstanceId)
        .messageEventSubscriptionName("Payment received")
        .singleResult();
runtimeService.messageEventReceived("Payment received", execution.getId());
----

Both methods have variants that also pass process variables. After the message, the process runs in the transaction of the call until the next wait state. If a following step throws an exception, the call fails, and the process stays at the event. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#throwing-a-message-event[Throwing a Message Event^] in the Flowable documentation.

[[signal-events]]
== Signal Events

A signal event throws a signal or catches it. A thrown signal reaches every event that waits for it: in all process instances, or only in the same process instance if the signal has the *Process instance* scope. Use signals to tell many process instances at once that something has happened, for example, that a shop has closed. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#signal-event-definitions[Signal Event Definitions^] in the Flowable documentation.

To add a signal event in the xref:menu-views/modeler-web.adoc[Modeler] view, click the *Change type* image:quick-start/change-type-icon.png[width="20"] icon of a start, intermediate, or boundary event and select a signal option.

[cols="1,3", options=header]
|===
|Event
|Usage

|[[signal-start-event]]Signal start event
|Starts a process instance when the signal is thrown. If several processes have a start event for the signal, each of them starts. In an xref:bpmn/bpmn-subprocesses.adoc#event-subprocess[event subprocess], starts the event subprocess and can be interrupting or non-interrupting. An embedded subprocess can't have a signal start event.

|[[signal-intermediate-catching-event]]Signal intermediate catching event
|The process waits at the event until the signal is thrown. The event is a xref:bpmn/transactions.adoc#waiting-states[wait state].

|Signal boundary event
|Catches the signal while the activity it is attached to is active. Can be interrupting or non-interrupting.

|[[signal-intermediate-throwing-event]]Signal intermediate throwing event
|Throws the signal. Then the process continues along the outgoing sequence flow.
|===

[[throwing-signals]]
=== Throwing Signals

Signal events refer to signal definitions of the process. A definition has an id, a name, and a xref:bpmn/bpmn-process.adoc#signal-definition[scope]. You can manage definitions in the process properties or add one from an event by selecting *Create new...* in its *Signal* field.

Your code throws a signal through `RuntimeService` and passes the signal name, not the id:

[source,java]
----
runtimeService.signalEventReceived("Shop closed");
----

The engine delivers a signal in the transaction of the code or process instance that throws it. If a catching process instance fails with an exception, the throwing side fails too, and its transaction rolls back. To deliver a signal asynchronously, set `flowable:async="true"` on the `signalEventDefinition` element of a throwing event in XML. The *Asynchronous* property only makes the event itself asynchronous. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#throwing-a-signal-event[Throwing a Signal Event^] in the Flowable documentation.

[[error-events]]
== Error Events

An error event throws or catches a BPMN error: a business error that the process handles on an alternative path, for example, a declined payment. Catching error events are always interrupting. Java code throws a BPMN error as `BpmnError`. Error events don't catch other exceptions, which roll back the transaction to the last xref:bpmn/transactions.adoc#waiting-states[wait state]. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#error-event-definitions[Error Event Definitions^] in the Flowable documentation and xref:error-handling.adoc[Error Handling].

To add an error event in the xref:menu-views/modeler-web.adoc[Modeler] view, click the *Change type* image:quick-start/change-type-icon.png[width="20"] icon of an end event, a boundary event, or a start event inside an event subprocess, and select an error option.

[cols="1,3", options=header]
|===
|Event
|Usage

|[[error-start-event]]Error start event
|Starts an xref:bpmn/bpmn-subprocesses.adoc#event-subprocess[event subprocess] when an error is thrown in the scope that contains the event subprocess. The option is available only for start events inside an event subprocess.

|[[error-boundary-event]]Error boundary event
|Catches errors thrown inside the activity it is attached to: by an error end event in a subprocess, or by Java code that a service task calls. Cancels the activity, and the process continues along the outgoing sequence flow of the event.

|[[error-end-event]]Error end event
|Throws the error and ends the current path.
|===

[[error-matching]]
=== Matching Errors

Error events refer to error definitions of the process. A definition has an id, a name, and an optional error code. You can manage definitions in the xref:bpmn/bpmn-process.adoc#properties[process properties] or add one from an event by selecting *Create new...* in its *Error* field.

The engine matches throwing and catching events by error code:

* An event with no error set, or with an error definition that has no code, catches any error.
* A throwing event with an error definition that has no code matches any catching event, so set a code for the errors that you throw.
* If an activity has several matching boundary events, the event with the same code takes precedence over a catch-all event.
* An error end event must refer to an error definition. Otherwise, the process fails when it reaches the event, with `Error Code must not be null`.
* Errors that Java code throws, such as `new BpmnError("PAYMENT_FAILED")`, are matched by their code in the same way.
* If no event catches the error, the engine throws an exception: `No catching boundary event found for error with errorCode ...`.

[[escalation-events]]
== Escalation Events

[.since]
Since Jmix 3.1

An escalation event reports a situation to an enclosing scope, which can react to it with or without interrupting the work in progress.

You can create escalation events in the xref:menu-views/modeler-web.adoc[Modeler] view, set their properties, and manage escalation definitions. To add an escalation event, click the *Change type* image:quick-start/change-type-icon.png[width="20"] icon of an intermediate, end, or boundary event, or of a start event inside an event subprocess, and select an escalation option.

[cols="1,3", options=header]
|===
|Event
|Usage

|Escalation start event
|Starts an xref:bpmn/bpmn-subprocesses.adoc#event-subprocess[event subprocess] when an escalation is thrown in the scope that contains the event subprocess. Can be interrupting or non-interrupting. The option is available only for start events inside an event subprocess.

|Escalation boundary event
|Catches escalations thrown inside the activity it is attached to, for example, an embedded subprocess. Can be interrupting or non-interrupting.

|Escalation intermediate throwing event
|Throws the escalation. Then the process continues along the outgoing sequence flow, unless an interrupting event has caught the escalation and canceled the enclosing scope.

|Escalation end event
|Throws the escalation and ends the current path.
|===

[[escalation-matching]]
=== Matching Escalations

Escalation events refer to escalation definitions of the process. A definition has an id, a name, and an optional escalation code. You can manage definitions in the xref:bpmn/bpmn-process.adoc#escalation-definition[process properties] or add one from an event by selecting *Create new...* in its *Escalation* field.

The engine matches throwing and catching events by escalation code:

* It looks for a catching event in the scope of the throwing event first, and then in the enclosing scopes.
* An event with no escalation set, or with an escalation definition that has no code, matches any escalation.
* If an activity has several matching boundary events, the event with the same code takes precedence over a catch-all event. An event subprocess inside an activity takes precedence over a boundary event attached to that activity.
* If no event catches the escalation, the engine ignores it. An uncaught error, in contrast, causes an exception at runtime.

----

[[compensation-events]]
== Compensation Events

Compensation undoes the work of activities that have completed, for example, cancels a hotel booking when the payment fails. A compensation throwing event runs the compensation handlers of these activities. See https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#compensation-intermediate-throwing-event[Compensation Intermediate Throwing Event^] and https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs#compensation-boundary-event[Compensation Boundary Event^] in the Flowable documentation.

To add a compensation event in the xref:menu-views/modeler-web.adoc[Modeler] view, click the *Change type* image:quick-start/change-type-icon.png[width="20"] icon of an intermediate or boundary event and select *Compensation intermediate throw event* or *Compensation boundary event*. To get a boundary event, drag an intermediate event from the palette onto the border of the activity.

[cols="1,3", options=header]
|===
|Event
|Usage

|[[compensation-boundary-event]]Compensation boundary event
|Attaches a compensation handler to an activity. To add the handler, click *Append compensation activity* in the context pad of the event. The Modeler view adds a task marked as a compensation handler and connects it to the event with an association. Change the task type as needed, for example, to a service task.

The event becomes active when the activity completes, and the handler runs once for each completion, for example, for each instance of a multi-instance activity. Flowable doesn't support compensation boundary events on embedded subprocesses: their handlers don't run.

|[[compensation-intermediate-throw-event]]Compensation intermediate throwing event
|Runs the compensation handlers of the completed activities in its scope: the process instance, or the subprocess that contains the event. Activities inside a subprocess are compensated only if the subprocess has completed. The handlers run in reverse order of completion; activities that completed in the same transaction can be compensated in any order. Then the process continues along the outgoing sequence flow. To compensate one activity only, set the `activityRef` attribute of the `compensateEventDefinition` element in XML.

|Compensation start event
|The Modeler view offers this option for start events inside an event subprocess, but Flowable doesn't support it: a process with such an event fails to deploy with `start event of event subprocess must be of type 'error', 'timer', 'message' or 'signal'`.
|===

In the Modeler view, compensation events have only the *Id* and *Name* properties.

[[compensation-example]]
=== Example

In this example, the `Book hotel` multi-instance task in the subprocess has a compensation boundary event with the `Cancel hotel booking` handler. If the `Charge credit card` task throws an error, its error boundary event leads to the `Cancel booking` compensation throwing event, which compensates the completed activities of the process:

* If the subprocess has completed, `Cancel hotel booking` runs once for each completed instance of `Book hotel`.
* If the subprocess is still active, for example, at the `Review booking` task, compensation doesn't reach the activities inside it, and `Cancel hotel booking` doesn't run.

image::bpmn-events/compensation-example.png[,600]

The XML of this example:

[source,xml]
----
<process id="booking" isExecutable="true">
  . . .
  <subProcess id="booking-subprocess">
    . . .
    <serviceTask id="book-hotel" name="Book hotel" ...>
      <multiInstanceLoopCharacteristics ... />
    </serviceTask>
    <boundaryEvent id="book-hotel-compensation" attachedToRef="book-hotel">
      <compensateEventDefinition /> <1>
    </boundaryEvent>
    <serviceTask id="cancel-hotel-booking" name="Cancel hotel booking"
        isForCompensation="true" ... /> <2>
    . . .
    <association id="compensation-association" associationDirection="One"
        sourceRef="book-hotel-compensation" targetRef="cancel-hotel-booking" /> <3>
  </subProcess>
  . . .
  <intermediateThrowEvent id="cancel-booking" name="Cancel booking">
    <compensateEventDefinition /> <4>
  </intermediateThrowEvent>
  . . .
</process>
----
<1> The compensation boundary event.
<2> The compensation handler.
<3> The association that connects the event and the handler.
<4> The compensation throwing event. It compensates all completed activities in its scope, which is the process.

[[bpmn-events-coverage]]
== BPMN Events Coverage

Jmix BPM doesn't support all BPMN 2.0 events. In the diagram below, unsupported events are marked in pink.

image::bpmn-events/jmix-events.png[]

The following events are not supported:

* Conditional events of all types
* Link events
* Message intermediate throwing events and message end events
* Signal end events
* Compensation start events and compensation end events

The Modeler view doesn't offer these events. The exception is compensation start events, which it offers inside event subprocesses, although a process with such an event fails to deploy. Conditional events are implemented in the Flowable engine but not supported in Jmix BPM. The other events are not implemented in Flowable either. See <<workarounds>> for ways to model similar logic.

[CAUTION]
====
A BPMN model created in another tool can contain unsupported events. The Modeler view shows them on the diagram, but some of them don't work as the BPMN specification defines:

* A process with a link event or a message intermediate throwing event fails to deploy.
* Message, signal, and compensation end events work as none end events: they end the path but don't send a message or a signal and don't trigger compensation.
====

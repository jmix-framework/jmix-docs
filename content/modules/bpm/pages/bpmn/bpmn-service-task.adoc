= Сервисная задача

[[overview]]
== Обзор

*Сервисная задача* используется для вызова Java-логики, внешних сервисов, API или автоматизированных приложений.

.*Графическая нотация*

Сервисная задача изображается как прямоугольник со скругленными углами и небольшим значком шестеренки в левом верхнем углу.

image::bpmn-service-task/service-task.png[,150]

.*XML-представление*

В зависимости от реализации XML-представление сервисной задачи может различаться. Примеры см. в описаниях соответствующих типов задачи.

[[task-type]]
== Тип задачи

*Task type* определяет, как вызывается Java-логика сервисной задачи:

* *Spring Bean*: укажите бин Spring, его метод и нужные параметры метода.

* *Java Delegate Class*: укажите класс, который реализует `JavaDelegate` или `FutureJavaDelegate`.

* *Expression*: вызовите выражение-метод.

* *Delegate Expression*: вычислите выражение, которое возвращает объект-делегат.

* *External Worker*: создайте задание, которое забирает и выполняет внешний обработчик.


[[spring-bean-service-task]]
=== Spring Bean

*Jmix BPM* позволяет вызвать из сервисной задачи метод бина Spring и передать ему значения параметров.

Существующий бин и его метод можно выбрать в полях **Bean Name** и **Method** соответственно.

После выбора метода появляются дополнительные поля для ввода значений аргументов метода.

Обратите внимание на флажок *is variable*. Он имеет смысл в основном для строковых параметров.
Если флажок не установлен, значение аргумента записывается в итоговое выражение в апострофах.
Если флажок установлен, апострофы не добавляются и в метод передается переменная с указанным именем.

* `${smpl_MyBean.someMethod('description')}` — это выражение использует строковое значение `description`.
* `${smpl_MyBean.someMethod(description)}` — это выражение использует значение переменной с именем `description`.

[[result-variable]]
==== Переменная результата

Если выбранный метод возвращает значение, появляется поле *Result variable*.
В нем можно указать одну из существующих переменных процесса или создать новую, просто введя ее имя.

[WARNING]
====
Следите за типами при использовании существующих переменных.
Если тип результата отличается от типа существующей переменной, создается новая переменная процесса с тем же именем.
Если была переменная `a1` типа `String`, а в нее сохраняется числовой результат `100L`, появится новая переменная `a1` типа `Long` со значением `100`.
====

Рядом с *Result variable* находится флажок *Use local scope*. Если флажок установлен, переменная результата, созданная сервисной задачей, получает локальную область в контексте исполнения задачи.
Это значит, что переменная доступна только в текущем исполнении и не передается в родительское исполнение или экземпляр процесса.

Этот параметр помогает изолировать переменную в конкретном исполнении сервисной задачи.
Если одновременно выполняется xref:bpm:bpmn/multi-instance-activities.adoc[несколько экземпляров] одной сервисной задачи,
у каждого экземпляра будет своя локальная переменная, и они не будут мешать друг другу.

.*XML-представление*

Вот как все параметры сервисной задачи с бином Spring представлены в XML:

[source,xml]
----
<serviceTask id="set-status-service-task" name="Set order status"
    flowable:async="true" <1>
    flowable:expression="${smpl_OrderStatusBean.setStatus(orderId,&#39;Sent&#39;)}" <2>
    flowable:resultVariable="quantity" <3>
    flowable:useLocalScopeForResultVariable="true" <4>
    jmix:taskType="springBean" jmix:beanName="smpl_OrderStatusBean"> <5>
  <extensionElements>
    <jmix:springBean beanName="smpl_OrderStatusBean"
     methodName="setStatus"> <6>
      <jmix:methodParam name="orderId" type="java.lang.String"
        isVariable="true">orderId</jmix:methodParam> <7>
      <jmix:methodParam name="status" type="java.lang.String"
        isVariable="false">Sent</jmix:methodParam> <8>
    </jmix:springBean>
  </extensionElements>
</serviceTask>
----
<1> флаг _Asynchronous_, по умолчанию `false` и не указывается.
<2> сгенерированное выражение, апострофы заменены на `&#39;`.
<3> переменная результата.
<4> флаг локальной области, по умолчанию `false` и не указывается.
<5> тип задачи.
<6> заданы имя бина Spring и метод.
<7> параметр передается как переменная процесса.
<8> параметр передается как значение.

[[process-variable-execution]]
==== Переменная процесса `execution`

Бин Spring не видит контекст процесса.
Но во многих случаях он нужен, например чтобы получить доступ к переменным процесса и свойствам текущей задачи.

Есть встроенная переменная процесса `execution` типа `DelegateExecution`, которую можно использовать как параметр метода бина Spring.
Создайте такой метод, например:

[source, java]
----
@Component("MyProcessBean")
public class MyProcessBean {

    public void mySampleMethod(DelegateExecution execution) { <1>
        String currentActivityId = execution.getCurrentActivityId();
        Set<String> variableNames = execution.getVariableNames();
        // etc.
    }
}
----
<1> параметр `execution`

Затем укажите этот метод в сервисной задаче:

image::bpmn-service-task/execution-as-parameter.png[,460]

[[java-delegate-service-task]]
=== Java Delegate Class

В этом случае бизнес-логику выполняет класс, который реализует интерфейс `org.flowable.engine.delegate.JavaDelegate` или `org.flowable.engine.delegate.FutureJavaDelegate` и переопределяет его метод _execute()_. Метод получает объект `execution` как параметр, поэтому у вас есть доступ к контексту процесса, включая все переменные процесса.

Если выбрать вариант _JavaDelegate class_ в поле *Task type*, можно выбрать подходящий класс:

image::bpmn-service-task/create-java-delegate.png[,460]

Например, реализуем класс, который создает переменную процесса со случайным значением:

[source,java]
----
public class RandomIndexJavaDelegate implements JavaDelegate {
    @Override
    public void execute(DelegateExecution execution) {
        long randomIndex = new Random().nextLong(100L);
        execution.setVariable("randomIndex", randomIndex);
    }
}
----

.*XML-представление*

Чтобы указать класс, вызываемый во время выполнения процесса,
нужно задать полное имя класса в атрибуте `flowable:class`.

[source,xml]
----
<serviceTask id="Activity_java_delegate" name="Java delegate"
    flowable:class="com.company.jmixbpmtraining.delegate.RandomIndexJavaDelegate" <1>
    jmix:taskType="javaDelegateClass"> <2>
  <extensionElements />
</serviceTask>
----
<1> указание класса Java Delegate.
<2> определение типа задачи.

[[instantiating-java-delegate]]
==== Создание экземпляра класса Java Delegate

Классы, которые используются в сервисных задачах типа _Java Delegate_, *не создаются при развертывании*.
Когда движок процессов впервые доходит до задачи во время выполнения, он создает экземпляр класса JavaDelegate.

Для сервисной задачи, в которой определен класс, создается только один экземпляр Java-класса.
Если несколько сервисных задач процесса ссылаются на один и тот же класс Java Delegate,
для каждой из них создается отдельный экземпляр.
Все экземпляры процесса используют общий экземпляр класса для задачи.

image::bpmn-service-task/java-delegate-instantiating.png[,600,role=light-background]

Поэтому класс не должен использовать поля экземпляра и должен быть потокобезопасным, так как он может выполняться одновременно из разных потоков.
Это также может влиять на xref:field-injections[инжектирование полей].


[[delegate-expression-service-task]]
=== Delegate Expression

*Выражение-делегат* (delegate expression) — мощная возможность сервисных задач, которая позволяет динамически получать Java-объект во время выполнения.
Например, выражение `$\{myServiceBean\}` будет разрешено в бин Spring с именем `myServiceBean`.

В контексте Spring выражения-делегаты могут напрямую ссылаться на бины Spring, что обеспечивает интеграцию с фреймворком Spring.
Это позволяет использовать инжектирование зависимостей и возможности Spring в реализации делегата.

Чтобы использовать классы-делегаты в выражениях-делегатах, добавьте к ним аннотацию `@Component`, как к бину Spring.
В этом случае класс сочетает возможности обоих типов — _бина Spring_ и класса _Java Delegate_:

[source,java]
----
@Component
public class MyDelegateExpression implements JavaDelegate {
    // Class fields and injections
    @Override
    public void execute(DelegateExecution execution) {
    // Required logic
    }
}
----

В результате из этого класса доступны контекст Spring и контекст процесса.
Чтобы вызвать его, используйте тип задачи _Delegate expression_. Например:

image::bpmn-service-task/delegate-expression.png[,473]

.*XML-представление*

Чтобы указать класс, вызываемый во время выполнения процесса, можно использовать выражение, которое возвращает объект.
Для этого в XML используется атрибут `flowable:delegateExpression`:

[source,xml]
----
<serviceTask id="delegate-expression"
    name="Delegate expression task"
    flowable:delegateExpression="${MyDelegateExpression}"
    jmix:taskType="delegateExpression">
</serviceTask>
----

В сервисной задаче можно использовать и выражение-значение.
Затем укажите переменную результата, и ей будет присвоен результат выражения.

[[external-worker-service-task]]
=== External Worker

Задача *External worker* создает задание внешнего обработчика Flowable и приостанавливает процесс, пока какой-нибудь обработчик не заберет и не выполнит это задание.
Внешний обработчик забирает задания через Java API или REST API, выполняет работу и сообщает результат обратно во Flowable.

Задача внешнего обработчика — это xref:bpm:bpmn/transactions.adoc#waiting-states[состояние ожидания].
Когда обработчик выполнит задание и сообщит об этом во Flowable, процесс продолжится.

.*XML-представление*

В BPMN XML задача внешнего обработчика представлена сервисной задачей с `flowable:type="external-worker"` и топиком:

[source,xml]
----
<serviceTask id="externalWorkerOrder"
    flowable:type="external-worker"
    flowable:topic="orderService" />
----

[[fail-retry]]
=== Повторные попытки при сбое

Как работают повторные попытки, см. в разделе xref:bpm:job-executor.adoc#failed-jobs[Повторные попытки и сбойные задания].

[[configuring-fail-retry]]
==== Настройка
Чтобы задать параметры *Fail retry*, используйте поле *Failed job retry time cycle* в разделе *Asynchronous execution* свойств сервисной задачи.
Поле показывается, только если выбрано *Asynchronous* или *Asynchronous leave*.
Если снять оба флажка, значение поля очищается.

image::bpmn-service-task/fail-retry-property.png[,460]

Значение должно быть выражением временного цикла по стандарту *ISO 8601*.
Пример `R5/PT7M` выше заставляет исполнитель заданий повторить задание 5 раз с паузой 7 минут между попытками.

*XML-представление*

Параметр повторных попыток задается элементом `flowable:failedJobRetryTimeCycle`.
Пример использования:

[source,xml]
----
<serviceTask id="failingServiceTask"
    flowable:async="true"
    flowable:class="org.flowable.engine.test.jobexecutor.RetryFailingDelegate">
    <extensionElements>
        <flowable:failedJobRetryTimeCycle>R5/PT7M</flowable:failedJobRetryTimeCycle>
    </extensionElements>
</serviceTask>
----

[[field-injections]]
=== Инжектирование полей

*Инжектирование полей* (field injections) — механизм Flowable для передачи параметров в класс Java Delegate в виде фиксированных строковых значений или выражений, которые разрешаются в строки.

Инжектируемое поле всегда должно иметь тип `org.flowable.common.engine.api.delegate.Expression`.
Когда инжектированное выражение разрешено, его можно привести к нужному целевому типу.

[WARNING]
====
Через _инжектирование полей_ нельзя передавать сущности или другие объекты. Фактически выражение разрешается в тип `String`.
Если строковое значение можно привести к вашему типу, все в порядке.
Иначе возникнет ошибка.
====

Как инжектировать поля:

. Определите поля в классе-делегате:
+
[source,java]
----
private Expression messageField;
private Expression quantityField;
----
. Выберите сервисную задачу и создайте поля с теми же именами, что и в коде. Значениями полей могут быть выражения или строки.
+
image::bpmn-service-task/field-injection-properties.png[,473]
+
[TIP]
====
Если нужно передать числовые значения, используйте выражение, как показано выше, например `$\{3\}`.
Если написать просто _3_, это будет интерпретировано как объект `String` `"3"`, который нельзя привести к типу `Integer`.
====

. Во время выполнения движок процессов разрешает выражения и передает получившиеся строки в класс-делегат.
. В классе Java Delegate должен быть код, который получает значения из полей и приводит их к нужным типам:
+
[source,java]
----
String message = (String) messageField.getValue(execution);
Integer quantity = (Integer) quantityField.getValue(execution);
----

[[field-injection-thread-safety]]
==== Инжектирование полей и потокобезопасность

В целом сервисные задачи с Java-делегатами и инжектированием полей потокобезопасны. Однако есть несколько ситуаций, в которых потокобезопасность не гарантируется: это зависит от настройки или окружения, в котором работает Flowable.

Тип задачи Java delegate class::
В этом случае инжектирование полей всегда потокобезопасно. Для каждой сервисной задачи, которая ссылается на определенный класс, создается новый экземпляр, и поля инжектируются один раз при создании экземпляра. Многократное использование одного класса в разных задачах или определениях процессов не создает проблем.
+
Учтите, что разные экземпляры процесса используют один и тот же экземпляр класса Java Delegate, на который ссылается задача.
Можно представить, что один экземпляр процесса влияет на другой, но это очень маловероятно.

Типы задачи Spring bean и expression::
Технически для Flowable сервисная задача с бином Spring представлена атрибутом `flowable:expression`.
+
При использовании атрибута `flowable:expression` инжектирование полей не нужно. Параметры передаются через вызовы методов, а они всегда потокобезопасны.
+
Строго говоря, инжектирование полей использовать можно, но не нужно.

Сервисная задача с delegate expression::
При использовании атрибута `flowable:delegateExpression` потокобезопасность экземпляра делегата зависит от того, как разрешается выражение. Если выражение-делегат повторно используется в разных задачах или определениях процессов и всегда возвращает один и тот же экземпляр, инжектирование полей не потокобезопасно.
+
Две сервисные задачи могут использовать одно и то же выражение-делегат, но инжектировать разные значения в поле `Expression`. Если выражение разрешается в один и тот же экземпляр, при одновременном выполнении процессов возможны состояния гонки при инжектировании поля someField.
+
Проще всего решить эту проблему одним из способов:
+
* Переписать Java Delegate так, чтобы использовать выражение или бин Spring и передавать нужные данные через аргументы метода.
* Возвращать новый экземпляр класса-делегата при каждом разрешении выражения-делегата. Например, при использовании Spring это значит, что для бина нужно задать область prototype (например, добавив к классу-делегату аннотацию `@Scope(SCOPE_PROTOTYPE)`).

****
Аннотация `@Scope(SCOPE_PROTOTYPE)` в Spring задает область бина: новый экземпляр бина создается при каждом запросе к контейнеру Spring.
В отличие от этого, при области singleton создается только один экземпляр бина, общий для всего приложения. Область prototype подходит для бинов, которые хранят состояние или не потокобезопасны.
****

*Пример*

[source,java]
----
public class UpperCaseJavaDelegate implements JavaDelegate {

    private Expression messageField;
    private Expression quantityField;
    @Override
    public void execute(DelegateExecution execution) {

        String message = (String) messageField.getValue(execution);
        Integer quantity = (Integer) quantityField.getValue(execution);

        String upperCaseMessage = message.toUpperCase();
        for (int i = 0; i < quantity; i++) {
            System.out.println(upperCaseMessage);
        }
    }
}
----

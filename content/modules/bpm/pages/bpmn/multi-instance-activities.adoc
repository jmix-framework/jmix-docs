= Множественный экземпляр

[[overview]]
== Обзор
*Действие с множественным экземпляром* — способ задать повторение шага бизнес-процесса.
В терминах программирования множественный экземпляр соответствует конструкции `for each`: он позволяет выполнить шаг
или даже целый подпроцесс для каждого элемента заданной коллекции, *последовательно* или *параллельно*.

Множественный экземпляр — это обычное действие с дополнительными свойствами (они называются _характеристиками множественного экземпляра_),
из-за которых во время выполнения действие выполняется несколько раз.
_Действием с множественным экземпляром_ могут стать следующие действия:

* Пользовательская задача
* Задача сценариев
* Сервисная задача
* Встроенный подпроцесс
* Вызов процесса

.*Графическая нотация*

Действия с множественным экземпляром изображаются как обычные действия
с маркером *параллельного* или *последовательного* выполнения в центре нижней части задачи или подпроцесса.
Три вертикальные линии означают, что экземпляры выполняются параллельно, а три горизонтальные — последовательно.

image::multi-instance/multi-instance.png[,350]

.*XML-представление*

Чтобы действие выполнялось как множественный экземпляр, у его XML-элемента должен быть дочерний элемент `multiInstanceLoopCharacteristics`.

[source,xml]
----
<multiInstanceLoopCharacteristics isSequential="false|true">
...
</multiInstanceLoopCharacteristics>
----

Атрибут *isSequential* указывает, выполняются ли экземпляры действия последовательно или параллельно.
По умолчанию этот атрибут не указывается, а его значение считается равным `false`.

[[special-variables]]
== Специальные переменные

Как требует спецификация BPMN 2.0, у каждого родительского исполнения для исполнений, созданных для экземпляров, есть следующие переменные:

[horizontal]
nrOfInstances:: Общее число экземпляров.

nrOfActiveInstances:: Число активных (еще не завершенных) экземпляров.
Для последовательного множественного экземпляра всегда равно 1.

nrOfCompletedInstances:: Число уже завершенных экземпляров.

Эти значения можно получить, вызвав метод _execution.getVariable(x)_.

Кроме того, у каждого созданного исполнения есть локальная переменная исполнения
(она не видна другим исполнениям и не хранится на уровне экземпляра процесса):

[horizontal]
loopCounter:: Индекс этого экземпляра в цикле for-each.

[[defining-number-of-instan]]
=== Число экземпляров

Число экземпляров можно задать двумя способами:

* *Напрямую* — с помощью параметра _Cardinality_.
* *По коллекции* — оно будет равно размеру коллекции.

При задании _cardinality_ можно использовать выражения, которые разрешаются в положительное число, например:

 ${nrOfOrders-nrOfCancellations}


Задание источника коллекции и коллекции:: Доступны разные источники: выражение,
переменная процесса и поставщик пользователей. В этом случае движок процессов создает столько действий, сколько элементов в коллекции.

image::multi-instance/collection-source-user-task.png[,463]

.*Задание коллекции выражением*
Передать коллекцию в действие с множественным экземпляром можно и выражением.
Выражение может содержать вызов метода бина, который возвращает список объектов:

 ${smpl_OrderService.getOrders()}

.*Задание коллекции переменной процесса*

Проще всего использовать в качестве источника коллекции переменную процесса.
Это может быть список сущностей, строк, чисел или любых нужных объектов.

[NOTE]
====
Для пользовательских задач это должен быть список имен пользователей (`String`) или список пользователей
(объектов класса `User` или класса, реализующего интерфейс `UserDetails`).

Кроме того, в этом случае доступен только один _Assignee source_ — *Expression*.
Если коллекция называется `usernames`, а ее элементы имеют тип `String`, выражение будет таким:

 ${usernames_item}

А если коллекция называется `users`, а ее элементы — объекты класса `User` или `UserDetails`, выражение будет таким:

 ${users_items.username}

Выражение можно изменить вручную, но делайте это осторожно.
====

.*Задание коллекции через UserProvider*
В третьем варианте можно реализовать *UserListProvider* и использовать список имен пользователей в действии с множественным экземпляром.

См. xref:bpmn/bpmn-user-task.adoc#user-list-provider[Поставщик списка пользователей] в разделе *Пользовательская задача*.

Когда задана _коллекция_, система автоматически создает _Element variable_.
Она играет роль переменной цикла в конструкции `for each`.
Переменную элемента можно переименовать.

[[completion-conditions]]
=== Условия завершения

Как правило, действие с множественным экземпляром завершается, когда завершены все экземпляры. Однако
можно задать выражение, которое вычисляется при каждом завершении экземпляра.

Когда это выражение становится истинным, все оставшиеся экземпляры уничтожаются, действие с множественным экземпляром завершается
и процесс продолжается. Такое выражение нужно задать в дочернем элементе *completionCondition*.

Например:

 ${nrOfCompletedInstances > nrOfActiveInstances}

Это значит, что, когда число выполненных задач превышает число активных экземпляров,
все оставшиеся задачи отбрасываются.

В выражении условия также можно вызывать методы бинов Spring:

 ${smpl_ErrorService.failure()}


[[using-local-variables]]
== Использование локальных переменных

Допустим, нужно построить процесс, в котором несколько исполнителей записывают значение переменной.
Например, несколько преподавателей оценивают работу студента. Или это может быть сервисная задача, которая записывает значение.

В этом случае в действии с множественным экземпляром нужно использовать локальные переменные.
Иначе каждый экземпляр будет перезаписывать значение переменной внешней области.

[[outcomes-based-conditions]]
== Условия на основе результатов

Если множественный экземпляр — это пользовательская задача с результатами (outcomes), можно организовать своего рода «голосование».

В этом случае система сохраняет решение каждого пользователя в так называемом _контейнере результатов_ —
переменной процесса типа `OutcomesContainer`.
После завершения всех экземпляров все результаты можно увидеть в этом контейнере.

Затем на потоках операций, исходящих из эксклюзивного или инклюзивного шлюза, можно использовать условия завершения следующих типов:

* Anyone completed with the outcome
* Everyone completed with the outcome
* No one completed with the outcome

Например, есть процесс с пользовательской задачей с множественным экземпляром и двумя результатами, `Yes` и `No`:

image::process-example-multi-user-task.png[,400]

Тогда можно использовать условие на основе результатов, например
«Все ответили _Yes_»:

[[boundary-events]]
== Граничные события

Множественный экземпляр — это обычное действие, поэтому на его границе можно определить граничное событие.
В случае прерывающего граничного события, когда событие перехвачено,
все еще активные экземпляры уничтожаются.

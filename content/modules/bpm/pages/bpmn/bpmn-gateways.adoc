= Условия и шлюзы
:page-aliases: bpm:bpmn/bpmn-sequence-flow.adoc

Потоки операций соединяют элементы процесса. Условия на потоках операций и шлюзы определяют, по какому пути пойдет процесс. В Jmix BPM условие можно задать выражением, результатом пользовательской задачи или результатом бизнес-задачи.

[[sequence-flows]]
== Потоки операций

Поток операций (sequence flow) — элемент BPMN, который задает порядок выполнения действий в бизнес-процессе.
Он определяет логическое движение работы или информации от одного действия к другому
и показывает, в какой последовательности должны выполняться задачи или подпроцессы.

Потоки операций соединяют два действия на диаграмме BPMN
и показывают направление движения процесса и зависимости между действиями.
Они играют важную роль в визуализации и моделировании хода работы в бизнес-процессе
и помогают сделать модель процесса ясной и последовательной.


[[graphical-flows]]
=== Графическое и XML-представление

Поток операций изображается стрелкой от исходного элемента к целевому.
Стрелка всегда указывает на целевой элемент.

image::bpmn-sequence-flows/graphical-flow.png[,100]

В XML-файле потоки операций представлены отдельными объектами среди других элементов BPMN:

[source, xml]
----
    <sequenceFlow id="Flow_1sjggq6" sourceRef="Event_15w11z6" targetRef="Gateway_0r2ejfv" />
----

В описании потока операций есть два атрибута XML: _sourceRef_ и _targetRef_,
которые ссылаются на элементы, где начинается и заканчивается стрелка.

[[incoming-and-outgoing]]
=== Входящие и исходящие потоки

Поток операций соединяет два действия, поэтому для первого он _исходящий_, а для второго — _входящий_.

image::bpmn-sequence-flows/incoming-outgoing-flows.png[,300]

Рекомендуется, чтобы у каждого действия был только один входящий и только один исходящий поток.

В XML-файле ссылки на потоки операций видны в описании соответствующего элемента BPMN:

[source,xml]
----
    <task id="Activity_1pncn0v" name="Activity">
      <incoming>Flow_1tncfsd</incoming>
      <outgoing>Flow_1nxsuoi</outgoing>
    </task>
----

[[conditional-flow]]
=== Условный поток операций

BPMN 2.0 определяет _условный поток_ как отдельный элемент нотации.
Графически он изображается как обычный поток операций с маленьким ромбом в начале соединительной линии,
см. ниже:

image::bpmn-sequence-flows/conditional-flow.png[,200]

Условный поток можно использовать только как _исходящий_ поток действия.
Условие вычисляется во время выполнения, чтобы определить, будет ли использован поток операций.

В *Jmix BPM* условие может быть у любого потока операций, но оно вычисляется и используется только там, где это нужно.

image::bpmn-sequence-flows/conditional-flow-example.png[,250]

[CAUTION]
====
Использовать условные потоки *крайне не рекомендуется* из-за риска ошибок.
Например, на рисунке выше процесс остановится, если условие равно _false_ и других путей нет.
====


[[default-flow]]
==== Поток операций по умолчанию

У всех задач и шлюзов BPMN 2.0 может быть поток операций по умолчанию.
Он выбирается только как _исходящий_ поток операций действия или шлюза.

Поток операций по умолчанию изображается как обычный поток операций с косой чертой в начале.

image::bpmn-sequence-flows/default-flow.png[,150]

Поведение потока по умолчанию зависит от элемента, с которым он используется.
Условия на потоке операций по умолчанию всегда игнорируются.

[[gateways-conditions]]
== Условия

Условие определяет, когда выбирается поток. В *Jmix BPM* условие можно задать из следующих источников:

* Выражение (Expression)
* Результаты пользовательской задачи (User task outcome)
* Результат бизнес-задачи (Business rule task result)

image::bpmn-gateways/condition-source.png[,400]

[CAUTION]
====
В эксклюзивном шлюзе проверьте, что у каждого исходящего потока, кроме потока по умолчанию, есть условие.
Шлюз считает пустое условие истинным и выбирает первый в порядке XML поток, условие которого истинно или пусто.
Текстовая подпись над стрелкой для движка ничего не значит.
====

[[expressions]]
=== Выражения

Это логическое выражение, которое может обращаться к переменным процесса и сравнивать их с литералами или другими переменными.
В нем также можно вызывать методы бинов Spring.

Например:

 ${orderAmount > 1000}
 ${price > 100 && price <= 500}
 ${accountant.username == "jane"}
 ${jbt_MyService.getRandom > 0.5}
 ${jbt_MyService.evaluateCondition()}

В последнем случае метод должен возвращать значение типа _boolean_.

[[user-task-outcomes]]
=== Результаты пользовательской задачи

Если в процессе есть пользовательская задача с результатами (outcomes), можно выбрать результат, который активирует этот поток.

image::bpmn-gateways/exclisive-gateway-task-outcome.png[]

Чтобы настроить условие на основе результата, выберите пользовательскую задачу, а затем результат.

Выбирая пользовательскую задачу для условия, убедитесь, что она выполняется *до* вычисления условия.
Иначе во время выполнения возникнет ошибка.

// image::exclusive-gateway-wrong-task.png[,300]
// image::exclusive-gateway-wrong-condition.png[,300]

*Условия и пользовательская задача с множественным экземпляром*

Если пользовательская задача выполняется как xref:bpm:bpmn/multi-instance-activities.adoc[множественный экземпляр],
появляется дополнительный параметр — _condition type_:

image::bpmn-gateways/outcome-based-condition-types.png[,300]

Доступны следующие варианты:

* Anyone completed with the outcome
* Everyone completed with the outcome
* No one completed with the outcome

С помощью этого параметра можно организовать своего рода голосование.
Например, этот поток будет выбран, если хотя бы один пользователь выполнил задачу с результатом `yes`.

image::bpmn-gateways/outcome-based-condition.png[,600]

[[business-rule-task-result]]
=== Результат бизнес-задачи

Задача xref:bpm:bpmn/bpmn-business-rule-task.adoc[бизнес-правила] возвращает результат,
который можно использовать в условии шлюза.

image::bpmn-gateways/exclusive-gateway-business-rule.png[,600]

Чтобы настроить условие на основе результата бизнес-правила,
выберите задачу бизнес-правила, выходную переменную таблицы решений и выходное значение.

Убедитесь, что выбранная задача бизнес-правила выполняется *до* шлюза.

[[gateways]]
== Шлюзы
Шлюзы управляют ходом процесса: они определяют, при каких условиях процесс должен пойти по разным путям.
Каждый тип шлюза направляет ход процесса по-своему, на основе условий или событий.

Шлюзы помогают моделировать точки принятия решений, ветвление, слияние и синхронизацию в процессе
и позволяют точно представлять более сложные и динамичные процессы.

[[gateway-types]]
=== Типы шлюзов

*Jmix BPM* поддерживает четыре типа шлюзов BPMN:

* Эксклюзивный шлюз
* Параллельный шлюз
* Инклюзивный шлюз
* Шлюз на основе событий

*Complex gateway* не поддерживается.

'''

[[forks-and-joins]]
=== Шлюзы разделения и слияния

Все шлюзы, кроме шлюза _на основе событий_, могут играть в модели процесса две роли:

* *Разделение* (fork) — процесс разделяется на несколько путей;
* *Слияние* (join) — пути объединяются.

Как правило, шлюзы разделения и слияния используются парами, но это не обязательно.
Если процесс разделился, каждый путь может продолжаться до _конечного события_.

[NOTE]
====
Шлюзы управляют ходом выполнения процесса, создавая
или поглощая xref:bpm:bpm-concepts.adoc#tokens[токены].
====

[[exclusive-gateway]]
== Эксклюзивный шлюз

Эксклюзивный шлюз (XOR-шлюз) используется, чтобы моделировать в процессе решение на основе данных, например
значений переменных процесса или значений, которые возвращает метод бина.

Когда исполнение доходит до этого шлюза,
все условия исходящих потоков операций вычисляются в том порядке, в котором определены потоки.

Для продолжения процесса выбирается *первый* поток операций, условие которого равно _true_.
Пустое условие всегда считается равным _true_.

«Первый» здесь означает порядок, в котором потоки операций определены в теле XML-файла,
а не обязательно порядок, в котором они перечислены в описании шлюза.

Это различие подчеркивает, что порядок потоков определяется структурой XML-файла,
а не их визуальным представлением или текстовым описанием в шлюзе.

Эксклюзивные шлюзы часто называют вопросами, например «Документ согласован?». Но у самого шлюза нет никакой внутренней логики.
Чтобы шлюз действительно работал, на исходящих потоках нужно задать условия. См. <<gateways-conditions>>.

[[exclusive-gateway-default-flow]]
=== Поток по умолчанию

Если один из исходящих потоков отмечен как поток по умолчанию (косой чертой),
он выбирается, только когда условия всех остальных потоков равны _false_.

Если у потока по умолчанию есть условие, оно игнорируется.

При моделировании эксклюзивного шлюза настоятельно рекомендуется использовать поток по умолчанию.
Но это не обязательно.

Поэтому не используйте эксклюзивный шлюз так, как на рисунке, где шлюз одновременно разделяет и объединяет пути:

'''

[[multiple-true-conditions]]
==== Несколько истинных условий

image::bpmn-gateways/exclusive-gateway-two-true-conditions.png[,250]

В этом примере у эксклюзивного шлюза два условия, и оба очевидно истинны.
Условие № 1 вычисляется первым, потому что в XML-файле процесса оно находится выше условия № 2.
Однако в описании шлюза первым стоит условие № 2.

[source, xml]
----
<process id="exclusion-gateway-demo" name="exclusion-gateway-demo" isExecutable="true">
    <exclusiveGateway id="Gateway_0r2ejfv"> <3>
      <incoming>Flow_1sjggq6</incoming>
      <outgoing>Flow_2</outgoing>
      <outgoing>Flow_1</outgoing>
    </exclusiveGateway>
    <endEvent id="Event_0kn6j1t" name="1">
      <incoming>Flow_1</incoming>
    </endEvent>
    <sequenceFlow id="Flow_1" name="1 &#62; 0" sourceRef="Gateway_0r2ejfv" targetRef="Event_0kn6j1t"> <2>
      <extensionElements>
        <jmix:conditionDetails conditionSource="expression" />
      </extensionElements>
      <conditionExpression xsi:type="tFormalExpression">${1&gt;0}</conditionExpression>
    </sequenceFlow>
    <endEvent id="Event_1wmb937" name="2">
      <incoming>Flow_2</incoming>
    </endEvent>
    <sequenceFlow id="Flow_2" name="2 &#62; 0" sourceRef="Gateway_0r2ejfv" targetRef="Event_1wmb937"> <1>
      <extensionElements>
        <jmix:conditionDetails conditionSource="expression" />
      </extensionElements>
      <conditionExpression xsi:type="tFormalExpression">${2&gt;0}</conditionExpression>
    </sequenceFlow>
    <startEvent id="Event_15w11z6">
      <outgoing>Flow_1sjggq6</outgoing>
    </startEvent>
    <sequenceFlow id="Flow_1sjggq6" sourceRef="Event_15w11z6" targetRef="Gateway_0r2ejfv" />
</process>
----
<1> поток операций с условием № 1
<2> поток операций с условием № 2
<3> раздел описания шлюза, поток № 2 перед № 1

[[cascades-exclusive-gateways]]
==== Каскады эксклюзивных шлюзов

Эксклюзивный шлюз работает как оператор `switch` в программировании, а не как `if`.
У него может быть сколько угодно исходящих потоков.

Поэтому не стоит строить каскады шлюзов «да — нет»:
для выбора нужного исходящего потока операций можно использовать более сложные условия.

Не моделируйте так:

image::bpmn-gateways/exclusive-gateway-cascade.png[,500]

Здесь два шлюза вычисляют простые условия _Sky == blue_ и _Sea == green_.
Если оба истинны, процесс идет дальше. Но модель выглядит сложной.

Более сложные условия позволяют обойтись без каскадов шлюзов:

image::bpmn-gateways/exclusive-gateway-no-cascade.png[,350]

На этом рисунке используется составное условие _Sky == blue && Sea == green_,
поэтому нужен только один шлюз.

[[parallel-gateway]]
== Параллельный шлюз

Параллельный шлюз (AND-шлюз) используется, чтобы разделить процесс на несколько параллельных путей
или объединить несколько параллельных путей обратно в один.

image::bpmn-gateways/parallel-gateway-example.png[,600]

Когда исполнение доходит до параллельного шлюза, процесс разделяется на столько путей, сколько у шлюза исходящих потоков.

Если есть параллельный шлюз слияния, процесс ждет, пока не будут выполнены все входящие потоки,
то есть пока все параллельные пути не дойдут до шлюза слияния.
Затем процесс продолжается после шлюза слияния.

На самом деле объединять параллельные пути не обязательно.
У каждого из них может быть свое _конечное событие_.
Но весь процесс завершается только после завершения *всех* параллельных путей.

==== Используйте каскады

Учтите, что параллельный шлюз не обязательно должен быть «сбалансированным»
(с одинаковым числом входящих и исходящих потоков операций у соответствующих параллельных шлюзов).

Параллельный шлюз просто ждет все входящие потоки операций и создает параллельный путь выполнения
для каждого исходящего потока операций, независимо от других конструкций модели процесса.

[[inclusive-gateway]]
== Инклюзивный шлюз

Инклюзивный шлюз (OR-шлюз) можно рассматривать как сочетание _эксклюзивного_ и _параллельного_ шлюзов.

Как и в эксклюзивном шлюзе, на исходящих потоках операций можно задать условия, и инклюзивный шлюз их вычислит.

Но главное отличие в том, что инклюзивный шлюз, как и параллельный, может выбрать больше одного потока операций.

От параллельного шлюза он отличается тем, что ждет только те входящие потоки, которые будут выполнены (их условия истинны).
После слияния процесс продолжается после инклюзивного шлюза.

image::bpmn-gateways/inclusive-gateway-example.png[,650]

В этом примере первый пользователь заполняет чек-лист, в котором отмечает, кто должен участвовать в согласовании.

[[event-based-gateway]]
== Шлюз на основе событий

Шлюз на основе событий позволяет принимать решение на основе событий.

У шлюза на основе событий должно быть не меньше двух исходящих потоков операций.
Каждый поток операций должен вести к промежуточному перехватывающему событию таймера, сообщения или сигнала.

Сразу после шлюза на основе событий никакие другие действия не допускаются.

Когда исполнение процесса доходит до шлюза на основе событий, шлюз работает как *состояние ожидания*: исполнение приостанавливается.

Кроме того, для каждого исходящего потока операций создается подписка на событие.

Процесс пойдет по пути того события, которое сработает первым.

Учтите, что потоки операций, исходящие из шлюза на основе событий, отличаются от обычных потоков операций.
Эти потоки операций на самом деле никогда «не выполняются».
Напротив,
они позволяют движку процессов определить, на какие события должно подписаться исполнение, пришедшее в *шлюз на основе событий*.

=== Использование шлюза на основе событий

Типичный случай использования шлюза на основе событий — запрос к ненадежному внешнему сервису.
Этот сервис может отказать или вернуть ошибку в любой момент, когда процесс отправляет запрос.

Со шлюзом на основе событий это можно смоделировать так, как показано на рисунке:

image::bpmn-gateways/event-based-gateway-usage.png[,500]

В этом примере сервисная задача отправляет запрос в сервис, а затем процесс доходит до шлюза на основе событий — состояния ожидания.

Здесь возможны три варианта:

* *Success* — получено сообщение OK, и процесс продолжает обычный путь.
* *Failure* — получено сообщение об ошибке, и его можно обработать. При необходимости для разных ошибок можно использовать разные сообщения.
* *Timeout* — время истекло, и нужно решить, что делать, например повторить запрос.

Такой шаблон делает диаграмму понятнее.

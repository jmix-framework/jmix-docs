= Event Listeners
:page-aliases: listeners.adoc

NOTE: You can use xref:bpm:bpmn/bpmn-user-task.adoc#notifications[notifications] of user tasks to send in-app messages and emails when a task is created, assigned, completed or deleted. Use the listeners described on this page for other reactions to process events.

You can make your code react to what happens in a process in three ways:

* <<element-listeners>>: execution and task listeners that you set on BPMN elements.
* <<engine-events>>: listeners of engine events, for all processes or for one process.
* <<spring-events-bpm>>: seven engine events that the BPM add-on publishes as Spring application events.

[[element-listeners]]
== Listeners on BPMN Elements

Execution and task listeners are part of the process definition. You set them on BPMN elements, and the engine calls them at points in the lifecycle of these elements.

[[execution-listeners]]
=== Execution Listeners

You can set execution listeners on the elements that have the *Execution listeners* property, see the element pages in the xref:bpm:bpmn/bpmn-elements.adoc[Element Reference].

In the xref:bpm:menu-views/modeler-web.adoc[Modeler] view, the *Execution listener editor* has the following fields:

* *Event*: *start* when the process execution reaches the element, *end* when it leaves the element, or *take* when it follows a sequence flow (sequence flows only).
* *Type*:
** *Java class*: a class that implements `org.flowable.engine.delegate.ExecutionListener` or `org.flowable.engine.delegate.JavaDelegate`. Select it in the *Class name* drop-down list.
** *Expression*: an expression that the engine evaluates, for example, a call of a Spring bean method.
** *Delegate expression*: an expression that returns a Spring bean, such as `+${myListener}+`. The drop-down list contains the Spring beans that implement `ExecutionListener` or `JavaDelegate`. You can also enter another expression.
* *Fields*: values for the listener fields.

The *Class name* drop-down list contains the classes of your application and Jmix add-ons that implement `ExecutionListener` or `JavaDelegate` themselves, not through a superclass. When you select a class, or a bean in the *Delegate expression* field, the editor adds the class fields of the `org.flowable.common.engine.api.delegate.Expression` type to the *Fields* section, so you only enter their values. The engine injects these values into the fields when it calls the listener, see https://flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs/#field-injection-on-execution-listeners[field injection^].

[[task-listeners]]
=== Task Listeners

A task listener is called on user task events: *create*, *assignment*, *complete* and *delete*. Only user tasks have task listeners.

For the order of the events, the task listener editor and an XML example, see xref:bpm:bpmn/bpmn-user-task.adoc#setting-task-listeners[Setting Task Listeners].

[[engine-events]]
== Engine Events

The process engine dispatches a typed event for each of its operations, for example, `PROCESS_STARTED`, `ACTIVITY_STARTED`, `TASK_ASSIGNED`, `TIMER_FIRED`, `JOB_EXECUTION_FAILURE` or `VARIABLE_UPDATED`. Events about engine entities also have an entity type, such as task or process instance. See https://flowable.com/open-source/docs/bpmn/ch03-Configuration/#event-handlers[Event handlers^] in the Flowable documentation.

A listener of engine events implements `org.flowable.common.engine.api.delegate.event.FlowableEventListener`. Its `isFailOnException()` method sets what happens if the listener throws an exception: with `true`, the exception fails the engine operation; with `false`, the engine logs the exception and continues.

[[engine-wide-event-listeners]]
=== Engine-Wide Event Listeners

You can register a listener for the engine events of all processes in the process engine configuration, see xref:bpm:process-engine.adoc#process-engine-configuration[Process Engine Configuration]. For the seven events that Jmix BPM publishes as <<spring-events-bpm,Spring events>>, a Spring event listener is simpler: it needs no engine configuration.

[[process-event-listeners]]
=== Process Event Listeners

A process can have Flowable event listeners. The engine calls them only for the events of this process definition and its process instances, such as `TASK_ASSIGNED` or `TIMER_FIRED`. See https://flowable.com/open-source/docs/bpmn/ch03-Configuration/#adding-listeners-to-process-definitions[Adding listeners to process definitions^] in the Flowable documentation.

In the Modeler view, you add process event listeners in the *Event listeners* section of the process properties. The *Event listener editor* has the following fields:

* *Type*:
** *Java class*: a class that implements `org.flowable.common.engine.api.delegate.event.FlowableEventListener`.
** *Delegate expression*: an expression that returns a Spring bean that implements `FlowableEventListener`.
* *Entity type*: the type of the entity whose events the listener receives, such as *Task* or *Process instance*.
* *Events*: the engine event types that the listener receives.

[[spring-events-bpm]]
== Jmix BPM Spring Events

The BPM add-on publishes seven engine events as Spring application events of the `io.jmix.bpm.engine.events` package. You receive them for all processes in a method of a Spring bean annotated with `@EventListener`, without any settings in the process.

[cols="1,2", options="header"]
|===
|Spring event
|Published when

|`ProcessStartedEvent`
|A process instance starts.

|`ProcessCompletedEvent`
|A process instance completes.

|`ActivityStartedEvent`
|The process execution reaches an activity.

|`ActivityCompletedEvent`
|An activity completes.

|`UserTaskCreatedEvent`
|A user task is created.

|`UserTaskAssignedEvent`
|The assignee of a user task changes.

|`UserTaskCompletedEvent`
|A user task is completed.
|===

The engine publishes these events synchronously, in the thread that changes the process and before the change is finished. So a listener runs with the permissions of the user whose action changed the process, and without an authenticated user when a timer or an asynchronous job changed it. If a listener throws an exception, the engine logs a warning and the process continues, but the remaining listeners of this event aren't called.

`UserTaskAssignedEvent` is also published when a task is created with an assignee and when a task is unassigned.

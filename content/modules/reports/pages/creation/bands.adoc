= Bands and Datasets

The internal report structure is composed of _bands_. A band represents a section of the report that may appear zero or more times in the final document.

A band is populated with data provided by one or multiple _datasets_ associated with the band.

In the report template, the bands are marked up in a way that depends on the file format. The report definition includes the hierarchical structure of bands, corresponding to the template bands.

The picture below shows an example of bands used in a report:

.Sample report bands
image::create/bands-1.svg[align="center", width="611"]

The `Root` band in the report definition is predefined, however, it may not be used in a template.

TIP: You can find examples of various bands and datasets in the xref:reports-guide:index.adoc[] guide.

[[bands]]
== Bands

You can define bands at runtime on the <<bands-tab,*Bands* tab>> of the report detail view or at design time with the <<band-def,@BandDef>> annotation.

[[bands-tab]]
=== Bands Tab

The *Bands* tab of the runtime report editor allows you to define the band hierarchy and datasets for each band.

image::bands.png[align="center",width="1079"]

A report band has the following parameters:

* *Name* -- band name, unique within the report. It must contain only Latin letters, numbers, and underscores.
+
NOTE: If the band name starts with *header*, its data will not be printed when using the xref:creation/templates.adoc#table_output[table formatter].

* *Orientation* -- band orientation: *Horizontal*, *Vertical* or *Crosstab*.
** *Horizontal* bands are copied downwards. They may contain sub-bands.
** *Vertical* bands are copied to the right.
** *Crosstab* bands are copied to the right and downwards as a matrix.

* *Parent* -- parent band.

* *Multiple Datasets* -- select this checkbox if you want to define more than one dataset for the band.

* *Streaming* -- select this checkbox to make the band a <<streaming-bands,streaming band>>.

* *Dataset type* -- <<datasets,the type>> of dataset.

Each band includes one or more datasets. When running a report, datasets are transformed into lists of rows, where each row contains a map of name-value pairs. A band appears in the report as many times as the number of rows in its longest dataset.

Fields defined in the report template are replaced with corresponding values from the dataset when the report is executed. When defining datasets, you can use xref:creation/parameters.adoc[report external parameters] and fields from other bands, which lets you link bands.

Each report has the *Root* band. You can create datasets in it and refer to their fields from other bands.

Note that the *Dataset name* column, available when working with multiple datasets, is for user convenience only.

[[band-def]]
=== @BandDef Annotation

The `@BandDef` allows you to define bands when creating a report at design time. It has the following attributes:

* `name` -- band name, unique within the report. It must contain only Latin letters, numbers, and underscores.
* `parent` -- name of the parent band. Can be omitted only for the `Root` band.
* `root` -- must be set to `true` only for the `Root` band. `false` by default.
* `orientation` -- band's orientation defined by the `Orientation` enum: `HORIZONTAL`, `VERTICAL`, `CROSS`. It's `HORIZONTAL` by default.
* `streaming` -- if `true`, the band is a <<streaming-bands,streaming band>>. It's `false` by default.
* `dataSets` -- datasets defined by the array of `@DataSetDef` annotations.

The report must include the definition of the `Root` band with `name = "Root"` and `root = true` attributes.

IMPORTANT: The order of `@BandDef` annotations in the report definition Java class is important. It affects the printing order of bands on the same level of the hierarchy.

[[streaming-bands]]
=== Streaming Bands

[.since]
Since Jmix 3.1

A streaming band reads its rows one by one from a database cursor and writes them to the XLSX document right away. The reporting engine keeps only the last rendered rows in memory and writes older rows to a temporary file. The data of other bands is loaded into memory as usual. To make a band streaming, select the *Streaming* checkbox on the <<bands-tab,*Bands* tab>> or set `streaming = true` in the <<band-def,@BandDef>> annotation.

A report with a streaming band must meet the following requirements:

* The report has only one streaming band.
* The streaming band is a first-level band, that is, a direct child of the `Root` band, and has no child bands.
* The streaming band has exactly one dataset of the <<structure_sql,SQL>> or <<structure_jpql,JPQL>> type.
* All bands of the report are horizontal.

The report detail view does not save a report definition that breaks these requirements. When the reporting engine renders the streaming band, it checks them and fails with an error that lists the unmet requirements.

Streaming works only with an `.xlsx` template that is not custom. With other templates, the reporting engine ignores the streaming setting, writes a warning to the log, and loads all data into memory. An `.xlsx` template must also follow the rules described in xref:creation/templates.adoc#template_xlsx_streaming[Templates with a Streaming Band].

The query of the streaming band runs in a separate read-only transaction that stays open while the band rows are written.

TIP: To tune streaming, use the xref:configuration.adoc#jmix.reports.streaming.fetch-size[jmix.reports.streaming.fetch-size], xref:configuration.adoc#jmix.reports.streaming.cursor-clear-interval[jmix.reports.streaming.cursor-clear-interval], and xref:configuration.adoc#jmix.reports.streaming.row-access-window-size[jmix.reports.streaming.row-access-window-size] application properties.

[[datasets]]
== Datasets

[[structure_sql]]
=== SQL Dataset

*SQL* dataset is produced as a result of SQL query execution. It is recommended to use aliases for query result fields using the `as` operator. It is also recommended to enclose the aliases in double quotes to prevent possible case conversion by the DBMS:

[source, sql,indent=0]
----
select u.name as "userName", u.login as "userLogin"
from user_ u
----

You can use report input parameters and parent bands fields in the query. Parameters should be addressed by name enclosed in `${}`, for example, `++${dateFrom}++`. Parent band fields should be addressed similarly, by adding the band name in front of the field name: `${band1.field1}`.

Below is an example of an SQL query with a `groupId` parameter, obtained from the `group` parent band and an external `enabled` parameter:

[source, sql,indent=0]
----
select u.name as "userName", u.login as "userLogin"
from user_ u
where u.group_id = ${group.groupId}
    and u.active = ${active}
    and u.deleted_date is null
----

[CAUTION]
====
You should manually include conditions to filter soft deleted records for SQL queries.
====

[[link_field]]
Merge multiple datasets::
+
--
The *Link field* is used to merge data from multiple datasets inside one band. It can be used when the whole data for the report row could not be received by a single query or a Groovy script.
--

[[data_store]]
Selecting data store::
+
--
By default, queries are executed on the main database. If you want to query an xref:data-model:data-stores.adoc#additional[additional data store], set its name in the *Data store* field.
--

[[query_preprocessing]]
Query preprocessing in bands::
+
--
If you need to modify the SQL/JPQL query dynamically depending on the report input parameters or the parameter values from the parent band, you can use the SQL preprocessing. The template engine enables you to modify SQL/JPQL queries using Groovy. In order to activate it, check the *Preprocess query as Groovy template* checkbox below the band editor. The resulting query will be processed by `GStringTemplateEngine` that will have access to:

* the report parameters: `${<parameter_name>}`,

* values from parent bands: `${<band_name>.<parameter_name>}`.

Let's consider the following example: depending on whether the `createTs2` report parameter is passed you need to select one of the query conditions: `e.create_ts < $\{createTs2\}` or `e.create_ts < current_timestamp`.

In this case, the query should look like this:

[source, sql,indent=0]
----
select e.create_ts, e.id, e.vin from ref_car e
where
e.create_ts >= ${createTs1}
and
<% out << (createTs2 != null  ? 'e.create_ts < ${createTs2}' : 'e.create_ts < current_timestamp')%>
----

Thus, if the `createTs2` parameter is not passed, the initial query will be transformed into the following resulting query:

[source, sql,indent=0]
----
select e.create_ts, e.id, e.vin from ref_car e
where
e.create_ts >= ${createTs1}
and
e.create_ts < current_timestamp
----

If `createTs2` is passed, the following resulting query will be used for the band:

[source, sql,indent=0]
----
select e.create_ts, e.id, e.vin from ref_car e
where
e.create_ts >= ${createTs1}
and
e.create_ts < ${createTs2}
----
--

[[structure_jpql]]
=== JPQL Dataset

*JPQL* dataset is produced as a result of JPQL query execution. The resulting query fields must have aliases provided using the `as` operator. Similar to an SQL query, you can use report input parameters and parent band fields in the JPQL query.

Below is an example of a JPQL query with a `groupId` parameter, obtained from the `group` parent band and an external `enabled` parameter:

[source, jpql,indent=0]
----
select u.name as userName, u.login as userLogin
from User u
where u.group.id = ${group.groupId}
    and u.active = ${active}
----

JPQL queries automatically support soft deletion and return only records that are not deleted.

[IMPORTANT]
====
When using a JPQL query as a data source for a report, please note that the query is executed directly against the database and bypasses xref:data-access:data-manager.adoc[DataManager]. This means that the system's regular xref:security:authorization.adoc#data-access-checks[data access security checks] (row-level and resource) are *not applied automatically*. You must ensure that your JPQL queries only retrieve data that the user is authorized to access. It is your responsibility to implement any necessary security checks in your queries.
====

You can also use *Link field* to <<link_field,merge multiple datasets>>, use *Data store* to <<data_store,query additional data store>> or activate <<query_preprocessing,query preprocessing>> by checking the *Preprocess query as Groovy template* checkbox below the band editor.

[[structure_llm]]
=== AI-generated JPQL Dataset

[.since]
Since Jmix 3.1

*AI-generated JPQL* dataset is produced as a result of JPQL query execution. The query itself is generated by a Large Language Model (LLM) from your description in natural language. The query is stored with the dataset. When the report runs, the stored query is executed through xref:data-access:data-manager.adoc[DataManager], and the LLM is not called.

[[llm-requirements]]
==== Requirements

The query is generated by the xref:ai-tools:index.adoc[AI Tools] add-on. The *AI-generated JPQL* dataset type is available in the report detail view if the add-on is installed in the application and its xref:ai-tools:properties.adoc#jmix.aitools.dataload.enabled[data load functionality] is enabled. The *Generate query* button also requires a xref:ai-tools:getting-started.adoc#configure-model[configured model]. Without a model, you can edit a stored query only by hand.

The add-on is not required to run reports that contain such datasets, for example, after xref:report-import-export.adoc[import].

NOTE: Instead of the AI Tools add-on, you can generate queries with your own bean that implements the `io.jmix.reports.llm.LlmDataQueryService` interface.

[[llm-generating-query]]
==== Generating Query

The model reads the data model through the xref:ai-tools:tools.adoc#data-loading[Data Load tools] of the AI Tools add-on, so it sees only the entities that the add-on xref:ai-tools:tools.adoc#exposed-model[exposes] to the current user. The add-on validates the generated query and asks the model to fix it if needed, as many times as the xref:ai-tools:properties.adoc#jmix.aitools.dataload.max-repair-attempts[jmix.aitools.dataload.max-repair-attempts] property allows.

To create a dataset of this type:

. Select *AI-generated JPQL* in the *Dataset type* field.
. In the *Prompt* field, describe the data the band needs, for example: `Orders placed since :dateFrom with the customer name and the order amount`, where `dateFrom` is a report parameter. Refer to parameters by the names described in <<llm-parameters>>.
. Click *Generate query*. The maximum generation time is defined by the xref:configuration.adoc#jmix.reports.client.llm-query-generation-timeout[jmix.reports.client.llm-query-generation-timeout] application property.
. Check the query in the *Generated query* field and the band fields in the *Columns* list.

The *Columns* list contains the names you use for the band fields in the report template, for example, `+${customerName}+`. The columns match the values of the `select` clause by position.

To change the query and the columns by hand, click the *Edit* button (pencil icon) next to the *Generate query* button. If you add, remove, or reorder values in the `select` clause, change the *Columns* list the same way. Otherwise, band fields get wrong values or stay empty. The view does not check this. Generating the query again replaces your changes.

[[llm-parameters]]
==== Parameters

The query refers to values by JPQL named parameters:

* Report xref:creation/parameters.adoc[input parameters] are available by their aliases, for example, `:dateFrom`.
* Fields of parent bands are available as `:<band>_<field>`, for example, `:Orders_customerId` for the `customerId` field of the `Orders` band. Fields of the `Root` band are not available.
+
The model knows the fields of a parent band only if the parent band has an AI-generated JPQL dataset with a stored query. For other parent datasets, such as JPQL or SQL, name the parameters in the prompt.

Some parameters need special handling:

* An empty optional parameter is passed as `null`. To make such a condition work, the query must check the parameter, for example, `(:customer is null or o.customer = :customer)`. The model is asked to add such checks. When you save the report definition, the view warns you about optional parameters that are compared without a check, because otherwise the band would be empty with no error.
* A parameter of the *List of entities* type is matched with `in`. If such a parameter is empty, the report run fails with an error.
* The case-insensitive parameter syntax `:(?i)name` is not supported, and a report run fails with an error. Use `lower(...) like :name` instead.

If the prompt asks for a number of rows, for example, `the top 5 customers by revenue`, the limit is stored with the query. In a child band, the limit is applied for each row of the parent band.

In a cross-tab band, you can use an AI-generated JPQL dataset for the cells. The fields of the column header dataset (`<band>_dynamic_header`) and the row header dataset (`<band>_master_data`) are passed to the query as list parameters named `:<dataset>_<field>`, for example, `:Sales_dynamic_header_month` for the `month` field of the `Sales_dynamic_header` dataset. To let the reporting engine link each result row to a cell, the query must return a column with the same name for both the column headers and the row headers, for example, `Sales_dynamic_header_month`.

[[llm-jpql-differences]]
==== Differences from JPQL Dataset

The query syntax and behavior differ from the <<structure_jpql,JPQL dataset>>:

[cols="1,2,2", options="header"]
|===
| |JPQL dataset |AI-generated JPQL dataset

|Report parameter
|`+${dateFrom}+`
|`:dateFrom`

|Parent band field
|`+${Orders.customerId}+`
|`:Orders_customerId`

|Field names
|Aliases after `as`, optionally in double quotes. The aliases are removed from the query before execution.
|The *Columns* list. Aliases stay in the query, so they cannot be in double quotes and cannot be JPQL reserved words, such as `count`, `date`, or `order`. If you replace a JPQL dataset with an AI-generated one, rename such aliases, for example, `count` to `orderCount`, and update the field names in the template.

|Query preprocessing
|<<query_preprocessing,Groovy template>>
|Not supported

|Data store
|Set in the *Data store* field. The main data store is used by default.
|Determined from the query: the data store of the entity that the first value in `select` belongs to. There is no *Data store* field.

|Data access checks
|Not applied, because the query bypasses `DataManager`
|Applied, see <<llm-data-access-checks>>
|===

[[llm-data-access-checks]]
==== Data Access Checks

Unlike the <<structure_jpql,JPQL dataset>>, an AI-generated JPQL dataset applies the xref:security:authorization.adoc#data-access-checks[data access checks] of the current user:

* The user must have the read permission for every entity that the query uses, including joined entities and subqueries. Otherwise, the report run fails with an access error.
* Attributes that the user cannot read are returned as `null`.
* The xref:security:row-level-roles.adoc#jpql-policy[JPQL policies] of all entities that the query reads are added to the query.

To keep these checks effective, a report run fails with an error if the stored query:

* Is not a `select` query, or uses the `SQL`, `FUNCTION`, `FUNC`, `OPERATOR`, `COLUMN`, or `TABLE` functions of EclipseLink.
* Selects whole entities, such as `select o` or `select o.customer`, instead of their attributes.
* Reads an entity that has a xref:security:row-level-roles.adoc#predicate-policy[predicate policy] for the `READ` operation. Use a JPQL policy instead.
* Reads an entity with a row-level policy that cannot be applied to the query: the entity is used only in a subquery or under more than one alias, or its policy has a join clause and it is not the entity that the query selects from.

[[llm-limitations]]
==== Limitations

* A band with an AI-generated JPQL dataset cannot be a <<streaming-bands,streaming band>>.
* Reports created at design time cannot use this dataset type, because the query is generated in the report detail view and stored in the report definition.

[[structure_groovy]]
=== Groovy Dataset

*Groovy* dataset is produced as a result of Groovy script execution. The script returns an object of the `List<Map<String, Object>>` type. Each element of this list - an object of the `Map<String, Object>` type - corresponds to one dataset record.

The following objects are passed into the script:

* `params` - external report parameters map. Below is an example to get a parameter value:
+
[source, groovy,indent=0]
----
def active = params['active']
----

* `parentBand` - parent band as an object of the `io.jmix.reports.yarg.structure.BandData` type. This object allows you to get a parent band field value by invoking the `getParameterValue()` method, for example:
+
[source, groovy,indent=0]
----
def groupId = parentBand.getParameterValue('groupId')
----

* `currentAuthentication` - an object of the `io.jmix.core.security.CurrentAuthentication` type associated with the currently authenticated user. For example:
+
[source, groovy,indent=0]
----
def user = currentAuthentication.getUser()
----

* `metadata` - an object of the `io.jmix.core.Metadata` type, providing access to the application metadata. For example:
+
[source, groovy,indent=0]
----
def metaClass = metadata.getClass('User')
----

* `dataManager` - an object of the `io.jmix.core.DataManager` type that provides CRUD functionality. For example:
+
[source, groovy,indent=0]
----
def book = dataManager.load(Book.class).id(bookId).fetchPlan("book.edit").one()
----

* `timeSource` - an object of the `io.jmix.core.TimeSource` type used to obtain the current time. For example:
+
[source, groovy,indent=0]
----
def currentDate = timeSource.currentTimestamp()
----

* `applicationContext` - an object of the `org.springframework.context.ApplicationContext` type that provides access to managed beans. For example:
+
[source, groovy,indent=0]
----
def accountService = applicationContext.getBean(AccountService);
----

[[structure_entity]]
=== Entity Dataset

*Entity* dataset consists of a single row and is produced using attributes of a single JPA entity instance and the entities related to it.

The data source is produced from an external parameter of the *Entity* type, which must be described in the *Parameters* tab. The value in the *Entity parameter name* field must match the parameter name.

The report template must contain fields with entity attribute names. Attribute names can use names in the existing fetch plan by checking *Use existing fetch plan* or can be selected by the *Select entity attributes* button.

[CAUTION]
====
As the reporting engine always reloads entities in the *Entity* dataset from the database, you cannot use it for DTO entities or JPA entity instances not saved to the database. Instead, use the <<structure_groovy,Groovy dataset>> and access the entity passed as a parameter in the following way:

[source,groovy,indent=0]
----
def entity = params['entity']

return [['title': entity.title,
        'description': entity.description]]
----
====

[[structure_list]]
=== List of Entities Dataset

*List of entities* dataset is produced using a list of JPA entity instances.

The data source is produced using an external parameter being a *List of entities*, which must be described in the *Parameters* tab. The value in the *List of entities parameter name* field must match the parameter alias.

The report template must contain fields with entity attribute names. Attribute names can use names in the existing fetch plan by checking *Use existing fetch plan* or can be selected by the *Select entity attributes* button.

[CAUTION]
====
As the reporting engine always reloads entities in the *List of entities* dataset from the database, you cannot use it for DTO entities or JPA entity instances not saved to the database. Instead, use the <<structure_groovy,Groovy dataset>> and access the list of entities passed as a parameter in the following way:

[source,groovy,indent=0]
----
return params['entities'].collect {[
    'title': it.title,
    'description': it.description
]}
----
====

[[structure_json]]
=== JSON Dataset

*JSON* dataset is generated from JSON data. This data can be received from the following sources:

. *Groovy script*
+
--
The script provided by the user is supposed to return JSON data as a string.

For example:

[source, json,indent=0]
----
include::example$/library/src/main/resources/com/company/library/reports/bands/json.groovy[]
----
--

. *URL*
+
--
The report engine will perform a GET HTTP query against the URL.

For example:

[source, plain,indent=0]
----
https://jsonplaceholder.typicode.com/users
----
--

. *Parameter*
+
--
The report external parameter of String type which contains the JSON data must be described in the *Parameters* tab.
--

The received JSON tree is queried using the JsonPath query. For example, you can use the `$.store.book[*]` JsonPath to return all books from the following JSON tree:

[source, json,indent=0]
----
include::example$/library/src/main/resources/com/company/library/reports/bands/json.json[]
----

For more details on JsonPath expressions, see the http://goessner.net/articles/JsonPath/[documentation^].

[CAUTION]
====
Fields output by the report that have `Date`, `DateTime`, or `Time` data types do not support the format defined by `java.text.SimpleDateFormat`. To set the correct format, you should write a Groovy script.

To do this, switch to the **Value formats** tab of the report detail view and open the xref:creation/value-formats.adoc[formatter] dialog. For example, for the field `bookPublication.dateTime`, the Groovy script looks like this:

[source, groovy,indent=0]
----
include::example$/library/src/main/resources/com/company/library/reports/bands/formatter_for_dates.groovy[]
----
====

[[data-set-def]]
=== @DataSetDef Annotation

The `@DataSetDef` annotation allows you to define datasets when creating a report at design time. It has the following attributes:

* `name` -- dataset name. It is used in datasets of the `DELEGATE` type to link the dataset definition with the method that returns the delegate.
+
In a cross-tab band (`@BandDef.orientation = Orientation.CROSS`), the datasets must have the following names:

** Column headers: `$\{band_name}_dynamic_header`
** Row headers: `$\{band_name}_master_data`
** Main content: `$\{band_name}`

* `type` -- dataset type defined by the `DataSetType` enum. Values of this enum correspond to the types of runtime datasets described above. The `LLM` value (<<structure_llm,AI-generated JPQL dataset>>) cannot be used at design time.
+
Usually, design-time reports use datasets of the `DELEGATE` type. In this case, they are linked by name with methods annotated with `@DataSetDelegate` annotation.

[[data-set-delegate]]
=== @DataSetDelegate Annotation

The `@DataSetDelegate` annotation allows you to define a method that returns a delegate for executing dataset logic. It has the `name` attribute, which should be equal to the name of the corresponding dataset.

The annotated method must not have any parameters and should return the `ReportDataLoader` functional interface.
